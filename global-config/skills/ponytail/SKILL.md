# /ponytail — ขี้เกียจอย่างมีวินัย (global)

ดัดแปลงแนวคิดจาก DietrichGebert/ponytail แต่ **ตัด persona ฝังถาวร + ultra mode ทิ้ง** เพราะตัวนั้นทำให้โมเดล "เบลอ/ขี้เกียจเกิน/ตัด requirement เงียบ ๆ". ที่เก็บมาคือแก่นจริง: *decision ladder + คำสั่ง review/audit* พร้อม guardrail กันมันไปกัดงานที่ต้องละเอียด

แก่น: **"โค้ดที่ดีที่สุดคือโค้ดที่ไม่ต้องเขียน"** — แต่ "ทำงานถูกจริง" มาก่อน "สั้น" เสมอ

## ขอบเขต (สำคัญ)
- เป็น **opt-in ต่อ task เดียว** ไม่ใช่ mode ค้าง (ตอนเรียกด้วย `/ponytail` เอง). จบ task แล้วกลับโหมดปกติ ไม่ลากไป task อื่นเอง
- ผู้ใช้สั่ง `/ponytail` หรือบ่นว่า "มันเยอะไป / over-engineer / เขียนสั้นกว่านี้ได้ไหม" → เปิด
- เลิก: ผู้ใช้บอก "พอ / normal mode" หรือขึ้น task ใหม่
- **นอกจากนี้ยัง trigger เชิงรุกได้เอง** ในเงื่อนไขแคบๆ ดู "Proactive trigger" ด้านล่าง — ต่างจาก opt-in ตรงที่ไม่ต้องรอผู้ใช้สั่ง แต่ยังจบตัวเองต่อจุด/ต่อ task เดียวเหมือนกัน ไม่ค้างเป็น mode

## Proactive trigger (บัญญัติ 2026-08-31 — เดิมเป็น opt-in ล้วน แทบไม่เคยถูกเรียกจริง)
เรียกไต่ ladder **โดยไม่ต้องรอผู้ใช้พิมพ์ `/ponytail`** ใน 2 จังหวะ — ทั้งคู่ต้อง**ประกาศ "Using ponytail to ..." ตามปกติเหมือนเรียกสกิลอื่นทุกครั้ง** (ตามกฎ using-superpowers ของ harness ไม่มีข้อยกเว้น silent ให้ ponytail):

**(1) Ad-hoc code write ตรงๆ** — เข้าเกณฑ์ครบทุกข้อ:
1. งานเล็ก/isolated จริง (แก้/เพิ่มโค้ดจุดเดียว ฟังก์ชันเดียว ไม่ใช่ฟีเจอร์ใหญ่หลายไฟล์) และ**ไม่ได้ผ่าน** brainstorming/writing-plans/plan-pro มาก่อน (ดูข้อ 2)
2. กำลังจะ**เขียนของใหม่** (helper/abstraction/dependency ใหม่) ไม่ใช่แค่แก้โค้ดที่มีอยู่
3. ไม่ใช่งานที่เข้า no-minimize zones (หมวด "🚫 ห้ามตัดทิ้งเด็ดขาด" ด้านล่าง — validation, error handling, security/anticheat, accessibility, test ที่ไม่ trivial, requirement ที่ผู้ใช้ขอตรงๆ) หรืองานประเภทที่หมวด "⚠️ กันอาการเบลอ" ด้านล่างเตือนไว้ว่าห้ามใช้โหมดนี้เลย (algorithm ยาก, debug ลึก, anticheat)
4. ผู้ใช้ไม่ได้ขอความละเอียด/robustness ตรงๆ ในเทิร์นนั้น

**(2) ระหว่างวางแผน (plan-pro / writing-plans)** — ตอนร่างแต่ละ task ที่มีการเขียนโค้ดใหม่ (helper/abstraction/dependency ใหม่) ในแผน ให้ไต่ ladder ก่อนเขียน task นั้นลงแผนด้วย แม้ตัวแผนโดยรวมจะเป็นงานใหญ่/หลายไฟล์ก็ตาม (ยังเข้าเกณฑ์ trigger ได้เป็นรายจุด ไม่ใช่ทั้งแผน) — จุดประสงค์: กัน task ที่ over-engineer หลุดเข้าไปในแผนตั้งแต่ต้น ไม่ใช่รอให้ตรวจตอนท้าย. ยังใช้ no-minimize zones เดียวกัน (ข้อ 3 บน) — task ที่เป็น algorithm/security/architecture core ของแผนไม่เข้าเกณฑ์นี้

ทั้งสองจังหวะ: **สงสัยว่าเข้าเกณฑ์หรือไม่ → ไม่ trigger** (เกณฑ์แคบไว้ก่อน กันไปกัดงานที่ควรละเอียด) ถ้าตัด/เลือกทางลัดจริงให้มาร์ค `# ponytail:` ตามปกติ

## Decision ladder — ถามตามลำดับก่อนเขียนของใหม่
1. **ของนี้ต้องมีจริงไหม?** (YAGNI — งานที่ไม่ได้ขอ/เผื่ออนาคตที่ยังไม่มา = ข้าม)
2. **stdlib / ภาษาทำให้แล้วหรือยัง?**
3. **เป็น native feature ของแพลตฟอร์มไหม?** (เช่น Ren'Py screen/transform/ATL, persistent, `renpy.*` มีอยู่แล้ว — อย่าเขียนเอง)
4. **dep ที่ลงไว้แล้วแก้ได้ไหม?**
5. **ทำเป็นบรรทัดเดียวได้ไหม?**
6. ถ้าผ่านครบ → เขียน **minimum ที่ทำงานถูก** ไม่ใส่ abstraction/boilerplate ที่ไม่มีใครขอ

หลัก: **ลบ > เพิ่ม**. ถ้าแก้ปัญหาได้ด้วยการลบโค้ด นั่นคือคำตอบที่ดีกว่า

## 🚫 ห้ามตัดทิ้งเด็ดขาด (no-minimize zones)
ladder ใช้กับ "โค้ดที่ไม่จำเป็น" เท่านั้น — ของพวกนี้ไม่ใช่ฟุ่มเฟือย ห้าม "ขี้เกียจ" ใส่:
- **input validation / boundary checks**
- **error handling** (ห้าม swallow error เงียบ ๆ เพื่อให้โค้ดสั้น)
- **security / anticheat / save-integrity** — งาน AC ในโปรเจกต์นี้ (RT_409/410/411, manifest, HMAC, defense-in-depth) เป็น **OFF-LIMITS** ตรงข้ามกับ ponytail โดยสิ้นเชิง. ห้ามใช้โหมดนี้ลดชั้นกันโกง/ลดความ thorough เด็ดขาด
- **accessibility**
- **อะไรก็ตามที่ผู้ใช้ขอมาตรง ๆ** (requirement ที่ระบุ = ห้ามตัดเอง ต้องถามก่อน)
- **test/self-check ของ logic ที่ไม่ trivial**

ถ้าจะลด requirement → **เสนอ แล้วถามก่อน** ห้ามตัดเงียบ ๆ

## ⚠️ กันอาการ "เบลอ/เมา/ขี้เกียจ" (จุดที่ ponytail ต้นฉบับพัง)
- "สั้น" ไม่ใช่ "ถูก" — ห้ามแลกความถูกต้อง/ครบถ้วนกับจำนวนบรรทัด
- ห้ามตอบลวก/อธิบายน้อยจนผู้ใช้ตามไม่ทัน. code-first ได้ แต่ต้องบอกว่า "ตัดอะไรออก เพราะอะไร" สั้น ๆ
- ห้าม "ท้าทาย requirement" แบบ extremist (อาการของ ultra mode). สงสัยว่า requirement เกินจำเป็น = ถาม ไม่ใช่ลบ
- ถ้างานนั้นเป็น algorithm ยาก / debug ลึก / anticheat → **อย่าใช้โหมดนี้** มันจะดึงให้คิดตื้น

## มาร์ค shortcut ที่จงใจ
ถ้าเลือกทางลัดที่ยอมรับ trade-off ไว้ ให้คอมเมนต์ `# ponytail: <ทำไม + ข้อจำกัด>` เพื่อให้ตามเก็บ/อธิบายภายหลังได้

## โหมด (default = full แบบมี guardrail ข้างบน)
- **lite** — สร้างตามที่ขอ แล้ว *เสนอ* ทางที่ขี้เกียจกว่าให้เลือก (ไม่บังคับ)
- **full** (ดีฟอลต์) — ไต่ ladder จริงจัง ภายใต้ no-minimize zones
- ~~ultra~~ — **ตัดออก**. ถ้าผู้ใช้ขอ ultra จริง ๆ ให้เตือนความเสี่ยงก่อนแล้วทำเฉพาะ task เล็กที่ไม่แตะ no-minimize zones

## review / audit (read-only — ปลอดภัย ใช้เมื่อไรก็ได้)
- **`/ponytail review`** — ดู diff/โค้ดที่เพิ่งแก้ ชี้จุด over-engineer (abstraction เกิน, โค้ดซ้ำ stdlib, dead code, เผื่ออนาคต) + เสนอเวอร์ชันสั้นกว่า ไม่แก้ให้เองจนกว่าจะสั่ง
- **`/ponytail audit`** — สแกนทั้งโปรเจกต์/โฟลเดอร์หา over-engineering เป็นรายการจัดลำดับ
- คู่กับของที่มีอยู่: `/simplify` (แก้ให้เลย), `/scrutinize` (ตั้งคำถาม intent), `poka-yoke` (กันพลาดตอนออกแบบ)
