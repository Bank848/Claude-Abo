## หน้าแรก/header ของรายงาน .docx: อย่าใส่ title ใหญ่ตัวหนา center แบบ thesis — เริ่มด้วยชื่อ-รหัสตรงๆ ชิดซ้าย ขนาดเท่าเนื้อความ (บัญญัติ 2026-09-10)
เคสจริง (DNN_Homework_Report): header เดิมมี title paragraph แยก ("Lab 5 Report: Introduction to Deep Neural Network") ตัวหนา ขนาดใหญ่กว่าหัวข้อ section (20pt vs 18pt) จัด center อยู่บนสุด ตามด้วยชื่อวิชา/ชื่อ-รหัสนักศึกษา center เหมือนกัน — user ทักว่า "ไม่ต้องมี title นี้ก็ได้ ให้เริ่มด้วยชื่อเราเลย" และบอกว่าดู "AI thesis style" (ตัวใหญ่ กึ่งกลาง) ไม่เหมือนการบ้านนักเรียนปกติที่ header มักแค่ชื่อ-รหัส-วิชาสั้นๆ ชิดซ้าย ไม่มี title แยกเป็นก้อนใหญ่ตัวหนา
- **Default สำหรับ header การบ้าน/รายงานที่ไม่ใช่ thesis/วิทยานิพนธ์จริง**: **ไม่ต้องมี title paragraph แยกต่างหาก** — เริ่มบรรทัดแรกด้วยชื่อ-รหัสนักศึกษา (หรือชื่อทุกคนถ้ามีหลายคน) ตามด้วยชื่อวิชา/รหัสวิชา แค่นั้นพอ ไม่ต้องมีบรรทัด "รายงานการทดลอง Lab X: ..." แยกเป็นหัวเรื่องใหญ่ด้านบนสุด (ถ้าจำเป็นต้องมีชื่อ lab จริงๆ ให้ใส่รวมในบรรทัดเดียวกับชื่อวิชา ไม่ใช่แยกเป็น title ต่างหาก)
- **จัด header ทั้งหมดชิดซ้าย (`LEFT`) ไม่ใช่ `CENTER`** และ**ขนาดฟอนต์เท่ากับเนื้อความปกติ ไม่ใหญ่กว่า ไม่ตัวหนา** — title ใหญ่ตัวหนา center ที่บนสุดเป็น pattern ของเอกสารทางการ/thesis/report ที่ generate โดยระบบอัตโนมัติ ไม่ใช่ท่าที่นักเรียนพิมพ์ส่งการบ้านเองตามปกติ
- ใช้ default นี้กับทุกรายงาน/การบ้าน .docx ที่ไม่ได้ระบุ format บังคับจากอาจารย์/สถาบันว่าต้องมี title page แบบทางการ — ถ้า user บอกว่ามี template/format บังคับ (เช่นต้องมี title page) ให้ทำตามนั้นแทน อย่าใช้ default นี้ทับ

## แปล .docx รายงานไทย → อังกฤษ: อย่าสลับ font เอง คง font เดิม (TH Sarabun New) ไว้เสมอ (บัญญัติ 2026-09-10)
รอบแรกที่แก้เคส DNN_Homework_Report ด้านล่าง เคยตัดสินใจเปลี่ยน font จาก TH Sarabun New (font เดิมของ user) ไปเป็น Times New Roman เอง **โดยไม่มี user ขอ** ด้วยเหตุผลที่คิดไปเองว่า "TH Sarabun New เป็น font ไทย ไม่เหมาะกับรายงานภาษาอังกฤษ" — user ท้วงกลับทันทีว่า "ทำไมไม่ใช้ TH Sarabun New เกิดไรขึ้น" เพราะ TH Sarabun New เป็น font มาตรฐานที่มหาวิทยาลัยไทยกำหนดให้ใช้ ครอบคลุมทั้งข้อความไทยและอังกฤษในรายงานเดียวกัน (ดู [[docx-th-sarabun-sizing]]) ไม่ใช่ font ที่ใช้ได้เฉพาะภาษาไทย
- **กฎ: ตอนแปล .docx จากไทยเป็นอังกฤษ (หรือสลับภาษาใดๆ) ห้ามเปลี่ยน font ของเอกสารเองโดยไม่มี user ขอ** — ใช้ font เดิมของไฟล์ต้นฉบับต่อไปเสมอ (อ่านจาก run ของ paragraph ที่มีอยู่แล้ว) ไม่ว่าจะเป็น TH Sarabun New หรือ font อื่นที่ user ตั้งไว้ก่อนหน้า เพราะ font ที่ user เลือกมักผูกกับข้อกำหนดของสถาบัน/อาจารย์ ไม่ใช่แค่รสนิยมส่วนตัวที่เปลี่ยนได้ตามใจ
- ปัญหา justify/spacing ที่แก้ (ดูหัวข้อถัดไป) เป็นคนละเรื่องกับ font — แก้ปัญหา alignment/lang tag ได้โดยไม่ต้องแตะชื่อ font เลย ถ้า user ไม่ได้ขอเปลี่ยน font ให้คงชื่อ font เดิมไว้ทั้งใน run, Normal style, `theme1.xml`, และ `styles.xml` (สอดคล้องกันหมดตั้งแต่ต้น ไม่ต้องมาไล่ patch ทีหลังแบบที่เกิดในรอบนี้)
- ถ้าคิดว่า font เดิมไม่เหมาะกับภาษาใหม่จริงๆ (เช่นไม่มี glyph รองรับ) ให้**ถาม user ก่อนเปลี่ยน** ไม่ใช่ตัดสินใจเปลี่ยนเงียบๆ แล้วให้ user มาทักทีหลัง

## แปล .docx รายงานไทย → อังกฤษ: ห้าม full justify กับ font/lang metadata ต้องเคลียร์ตาม (บัญญัติ 2026-09-10)
เคสจริง (DNN_Homework_Report — CPE 342 Lab 5): แก้ script แทนที่ paragraph text ทีละ run จากไทยเป็นอังกฤษ (เก็บ bold/size เดิมไว้) ส่งไฟล์ไปแล้ว user บ่นว่า "ฟอนต์ผิด การจัดวางเพี้ยนหมดเลย" และ "การแบ่งบรรทัดกับประโยคเพี้ยน เยอะมาก เคาะเยอะเกิน" — ตรวจ PDF render (ผ่าน `mcp__word__convert_to_pdf`) แล้วพบสาเหตุจริง 3 จุด ไม่ใช่แค่จุดเดียว:

1. **ต้นฉบับไทยใช้ `WD_ALIGN_PARAGRAPH.THAI_JUSTIFY` (character-spaced justify) กับ paragraph บรรยาย — ห้าม map ตรงไปเป็น `JUSTIFY` แบบตะวันตก (word-spaced) ตอนแปลเป็นอังกฤษ.** Full justify แบบตะวันตกกระจาย extra space เฉพาะ "ระหว่างคำ" ไม่ใช่ระหว่างตัวอักษร — พอเนื้อหามีคำเทคนิค/โค้ดที่ตัดคำ (hyphenate) ไม่ได้เยอะ (เช่น `categorical_crossentropy`, `to_categorical`, `val_accuracy`) แต่ละบรรทัดจะถูกดันให้ช่องว่างระหว่างคำที่เหลือกว้างผิดปกติ (river of whitespace) — คนอ่านเห็นเป็น "เคาะเยอะเกิน/บรรทัดเพี้ยน" ตรงตามที่ user บ่น **ทางแก้: paragraph ที่แปลจากไทยเป็นอังกฤษ ให้ตั้งเป็น `WD_ALIGN_PARAGRAPH.LEFT` (ragged-right) แทน ไม่ใช่ JUSTIFY ใดๆ ทั้งสิ้น** เว้นแต่ user ขอ full justify ตรงๆ และเนื้อหาไม่มีคำยาวที่ตัดไม่ได้เยอะ
2. **`w:lang w:bidi="th-TH"` ที่ค้างมาจาก run เดิม (ภาษาไทยใช้ bidi tag สำหรับ complex-script line-breaking แม้ไทยจะไม่ใช่ RTL) ต้อง set ใหม่เป็น `en-US` ทั้ง `w:val` และ `w:eastAsia`, ลบ `w:bidi` ทิ้ง** — ถ้าปล่อยค้างไว้ บาง renderer อาจยังใช้กฎ line-break/justify แบบ complex-script กับ run ที่เนื้อหาเป็นอังกฤษล้วนแล้ว ทำให้จัดบรรทัดเพี้ยนเพิ่มอีกชั้น
3. **อย่า set `w:eastAsia` font ให้เป็นชื่อ font ละติน (เช่น "Times New Roman") ตรงๆ** — เคยลองทำตอนแรกโดยหวังว่าจะ "กันฟอนต์ตกไปใช้อย่างอื่น" แต่จริงๆ แล้วทำให้ font metric ของช่อง east-asian เพี้ยนไปจากที่ renderer คาดหวัง (ควรเป็น theme font หรือปล่อยว่างไปเลย ไม่ต้อง override ถ้า run เป็นอังกฤษล้วนไม่มีเนื้อหาเอเชียตะวันออกปน) — ลบ attribute นี้ทิ้งดีกว่า set เป็นชื่อ font ละติน
4. **Normal style (`d.styles['Normal']`) ที่มาจาก docDefaults/styles.xml เดิมยังชี้ไปที่ font ภาษาไทย (เช่น "TH Sarabun New") แม้จะเปลี่ยน font ของทุก run ที่มองเห็นแล้วก็ตาม** — paragraph-mark (ตัวอักษรจบย่อหน้าที่มองไม่เห็น) อ้างอิง Normal style นี้อยู่ ถ้าไม่แก้ font ของ Normal style ด้วย จะมี font สองชนิดปนกันในระดับ metric การคำนวณความสูงบรรทัดต่อย่อหน้า อาจทำให้ spacing ไม่สม่ำเสมอระหว่างย่อหน้า **ต้อง set `d.styles['Normal'].font.name` (และ rFonts ascii/hAnsi/cs ใน XML) ให้ตรงกับ font ที่ใช้จริงในเนื้อหาด้วยเสมอ ไม่ใช่แค่ per-run**
5. **ห้ามพิมพ์ multiple space (เว้นวรรคติดกันหลายตัว) เป็น separator ในข้อความ** เช่นบรรทัดชื่อ-รหัสนักศึกษาหลายคนที่คั่นด้วย "   " (3-6 ช่องว่างติดกัน) — ใช้ comma + single space (`, `) หรือ tab stop จริงแทน ไม่ใช่ raw space string เพราะ inconsistent spacing ที่มองไม่เห็นชัดในโค้ดแต่เห็นชัดตอน render จริง
6. **ไม่พอแค่แก้ font ของ run/Normal style — ต้องเช็ค `word/theme/theme1.xml` และ `word/styles.xml` ทั้งไฟล์ด้วยว่าไม่เหลือชื่อ font เดิมค้างอยู่เลย** เคสนี้แก้ font ของทุก run ที่มองเห็น + Normal style ไปแล้ว ยังเหลือ `TH Sarabun New` ค้างอยู่ 24 จุดใน `document.xml` (paragraph ว่างที่เป็นตัวเว้นบรรทัดระหว่าง section — เนื้อ text ว่างแต่ rPr ยังอ้าง font เดิม) และค้างเต็ม `theme1.xml` (majorFont/minorFont ที่ Word แสดงเป็น "ฟอนต์ของธีม" บนสุดของ font-picker dropdown) กับ `styles.xml` — user เปิด font dropdown เจอ "TH Sarabun New (หัวเรื่อง)/(เนื้อความ)" อยู่หัวลิสต์ theme font แล้วเข้าใจว่า "ฟอนต์ยังผิด" ทั้งที่ข้อความที่มองเห็นจริงเรนเดอร์เป็น Times New Roman ถูกแล้ว (การเช็คด้วย box ชื่อฟอนต์ตอน select-all ไม่พอ ต้องเช็คว่าไม่มีชื่อ font เดิมหลงเหลือในไฟล์ XML ทั้งไฟล์เลย ไม่ใช่แค่ใน run ที่มีเนื้อหา) **วิธีเช็คเร็ว**: เปิดไฟล์เป็น zip, `zipfile.read('word/document.xml'|'word/styles.xml'|'word/theme/theme1.xml').decode('utf-8').count('<ชื่อ font เดิม>')` ต้องได้ 0 ทั้งสามไฟล์ก่อนส่งให้ user ถ้าไม่ใช่ 0 ให้ string-replace ทั้งไฟล์ (ธีม font มักมีทั้ง `latin`/`cs`/บาง script อื่นที่ตั้งเป็น font เดิมด้วย ไม่ใช่แค่ตัวเดียว)
7. **วิธี verify ก่อนส่งไฟล์ให้ user (แทนการอ่านแค่ XML/text dump ที่ไม่เห็น layout จริง)**: มี `mcp__word__convert_to_pdf` (Word MCP) ให้ใช้ได้ตรงๆ — แปลง .docx → .pdf แล้ว Read tool อ่านเป็นภาพต่อหน้าดู layout จริงก่อนส่ง ถ้าไม่มี Word MCP ต่ออยู่ ให้บอก user ตรงๆ ว่าตรวจแค่ XML ไม่เห็น layout จริง อย่าฟันธงว่า "จัดหน้าถูกแล้ว" จากการอ่านแค่ paragraph text/XML เท่านั้น
- ใช้ checklist นี้ทุกครั้งที่แปล/แก้ font ของ .docx ที่มีเนื้อหาข้ามภาษา (ไทย↔อังกฤษ) ไม่ใช่แค่ตอนสร้างใหม่ทั้งฉบับ — เกี่ยวเนื่องกับ checklist "Layout polish" ด้านล่างที่ครอบเคส pagination/table แยกหน้า คนละปัญหากัน ใช้คู่กันได้

## Layout polish รอบสอง: อย่าทับงานที่ user แก้ต่อเองใน Word + checklist จัดหน้า (บัญญัติ 2026-09-10)
เคสจริง (PRE380 Engineering Economy Assessment #3): หลังส่งฉบับแก้คำหลายรอบจนเนื้อหาไม่มีกลิ่น AI แล้ว user เอาไฟล์ไปแก้ต่อเองใน Word (เติมชื่อ-รหัสนักศึกษา, แปะรูปโจทย์) แล้วขอให้ "แก้ docx" ต่อเรื่อง layout — **เกือบรัน `build_solution.py` ทับไฟล์เดิมไปเฉยๆ ซึ่งจะลบชื่อ/รหัส/รูปที่ user เพิ่งเติมทิ้งหมด**

**กฎที่ต้องทำก่อนแก้ไฟล์ .docx ที่เคยส่งให้ user ไปแล้วทุกครั้ง**: เปิดไฟล์ปัจจุบันด้วย python-docx เช็คก่อนว่า paragraph/image/table ตรงกับสิ่งที่ script ล่าสุด generate ไว้ไหม (โดยเฉพาะเช็ค `len(doc.inline_shapes)` และเนื้อหา paragraph ต้นๆ อย่างช่องชื่อ-รหัส) ถ้าไม่ตรง (มี image เพิ่ม, ข้อความถูกแก้) แปลว่า user แก้ไฟล์ต่อเองนอกสคริปต์แล้ว — **ห้ามรัน generator script ทับอีก** ให้เขียน script ใหม่ที่เปิดไฟล์ปัจจุบัน (`Document(path)`) มาแก้ต่อแบบ in-place เท่านั้น เพื่อรักษาสิ่งที่ user เพิ่มเข้าไปเอง

**Layout checklist สำหรับรายงาน .docx ที่ user บ่นว่า "ยังดูเหมือนจัดหน้าอัตโนมัติ"** (ถูกเนื้อหาแล้วแต่ layout ยังไม่ธรรมชาติ):
- ตารางแตกข้ามหน้า → ตั้ง `w:tblHeader` (repeat header row) + `w:cantSplit` ทุกแถว (ป้องกันแถวถูกตัดครึ่งข้ามหน้า) ผ่าน oxml โดยตรง เพราะ python-docx ไม่มี high-level API ให้ตั้งสองอย่างนี้
- หัวข้อทั้งหมด font size เท่ากันหมดดูแบน ไม่มี hierarchy → แยกขนาดตามระดับ (หัวข้อเลข "1./2." ใหญ่กว่า หัวข้อย่อย/บรรทัด "สรุปข้อ" เล็กกว่า) โดยยังคง **ห้ามใช้ Word Heading style** ตามกฎเดิมข้อ 1 ด้านบน แค่ปรับ `run.font.size` ให้ต่างกันบน Normal style
- สูตรคำนวณ (`PW = ...`, `= ...`, บรรทัดผลลัพธ์) อยู่ชิดขอบเหมือน paragraph ทั่วไป → เยื้อง `paragraph_format.left_indent` เข้า ~0.8 ซม. + ลด `space_before/after` ให้ชิดกันเป็นกลุ่มสูตรเดียวกัน แยกจาก paragraph บรรยาย
- ตารางสรุปคอลัมน์กว้าง/แคบไม่บาลานซ์ (หัวคอลัมน์ยาวตกบรรทัด) → set `table.autofit = False` แล้วกำหนด `cell.width`/`column.width` เป็น `Cm(...)` เองทุกคอลัมน์ (ต้อง set ทั้ง cell และ column ไม่ใช่แค่อย่างใดอย่างหนึ่ง ไม่งั้น Word บางเวอร์ชันไม่ยึดตาม)
- ช่องว่างระหว่าง section ไม่เท่ากัน (ต้องสงสัยว่าใช้ Enter/กด paragraph ว่างแทน spacing) → หาพารากราฟว่าง (`p.text.strip() == ""`) ที่อยู่ติดกันเกิน 1 ตัวแล้วลบส่วนเกินออก ใช้ `paragraph_format.space_before/after` คุม spacing แทนพารากราฟว่าง
- รูปภาพที่ user แปะเองเล็กไป/ไม่กึ่งกลาง → อ่าน `doc.inline_shapes` ปรับ `shape.width/height` (คูณ scale factor เก็บ aspect ratio เดิม) แล้ว set alignment ของ paragraph ที่ครอบรูปเป็น CENTER (หา paragraph ผ่าน `shape._inline.getparent().getparent()`)
- **ข้อจำกัดที่ต้องบอก user ตรงๆ**: python-docx ไม่ render หน้าเอกสารจริง จึงบอกไม่ได้ 100% ว่าตารางจะอยู่หน้าเดียวจบหรือหน้า 6 จะไม่เหลือว่างอีกหลังแก้ — ทำได้แค่ apply best-practice settings (repeat header, cantSplit, ลด spacing) แล้วให้ user เปิดใน Word ยืนยันเองว่า pagination โอเคจริงไหม อย่าอ้างว่า "แก้ตรงตามที่ขอแล้ว" แบบมั่นใจเกินสิ่งที่ตรวจสอบได้จริง
- เกี่ยวเนื่องกับ [[thai-writing-anti-ai-tell]] ที่ครอบเรื่องเนื้อหา/ถ้อยคำ — ไฟล์นี้ครอบเฉพาะโครงสร้างเอกสารและ layout เท่านั้น สองสกิลนี้ใช้คู่กันตอนทำรายงาน .docx ให้ user

## Layout polish รอบสาม: บังคับตารางขึ้นหน้าใหม่ + กัน table แตกหน้าแบบจริงจัง (บัญญัติ 2026-09-10 รอบ 2)
รอบ "repeat header row + cantSplit" (รอบสองด้านบน) ไม่พอเสมอไป — ถ้าตารางยังใหญ่กว่าที่เหลือของหน้าปัจจุบัน มันจะยังโดนดันแตกอยู่ดี (cantSplit ป้องกันแค่ "แถวเดียว" ไม่ขาดครึ่ง ไม่ได้ป้องกันทั้งตารางแยกหน้า) ต้องมี 2 เทคนิคเพิ่มเมื่อ user ขอ "ให้ตารางทั้งก้อนไปอยู่หน้าใหม่เลย ไม่ต้องพยายามยัดหน้าเดิม":

1. **บังคับ page break ก่อนตารางเป๊ะ ๆ (ไม่ใช่ก่อนพารากราฟก่อนหน้า)**: สร้าง paragraph ว่างใหม่ (`doc.add_paragraph()`) ตั้ง `paragraph_format.page_break_before = True`, `space_before/after = Pt(0)`, ลด font run ให้เล็กสุด (`Pt(1)`) กันมันกินพื้นที่เกิน แล้วย้าย element ไปวางก่อนตารางด้วย `table._tbl.addprevious(break_paragraph._p)` — ห้ามตั้ง `page_break_before` บน paragraph ที่มีอยู่ก่อนตาราง เพราะจะดันเนื้อหาอื่นในพารากราฟนั้นขึ้นหน้าใหม่ไปด้วยทั้งที่ไม่ได้ตั้งใจ
2. **กันทั้งตารางไม่ให้แยกหน้า (ไม่ใช่แค่กันแถวเดียวแตก)**: ตั้ง `keep_with_next = True` บน paragraph ของทุก cell ในทุกแถว **ยกเว้นแถวสุดท้าย** (แถวสุดท้ายต้อง "จบ" ได้ปกติ ไม่งั้น Word จะพยายาม keep กับเนื้อหาถัดจากตารางไปด้วยอีกที) ผสมกับ `cantSplit` ต่อแถวจากรอบสอง — สองอย่างนี้รวมกันคือ signal ให้ Word ดันทั้งตารางไปหน้าถัดไปเป็นก้อนเดียวถ้าตารางไม่พอดีที่เหลือของหน้าปัจจุบัน แทนที่จะปล่อยแตกกลางตาราง
- **เคสจริง**: PRE380 Assessment #3 ตารางสรุปข้อ 2 (2 แถวข้อมูล) มีแถว "Land Application" โผล่บนสุดหน้า 6 แบบไม่มีหัวตาราง ทั้งที่ทำ cantSplit ไปแล้วในรอบก่อน — เพราะ cantSplit ป้องกันแค่ "หัวตารางไม่หลุด" ผ่าน `tblHeader` แต่ไม่ได้ผูกทั้งก้อนเข้าด้วยกัน ต้องเพิ่ม keepNext ตามข้อ 2 ถึงแก้จริง
- ใช้คู่กับ checklist รอบสองด้านบน ไม่ใช่แทนที่ — เริ่มจาก repeat-header+cantSplit ก่อนเสมอ ค่อยเพิ่ม page-break-before/keepNext เมื่อ user ยืนยันว่ายังไม่พอ (การันตี layout แม่นยำ 100% ทำไม่ได้เพราะ python-docx ไม่ render จริงตามที่บันทึกไว้ในรอบสอง)

### รอบสามยังไม่พอ — ต้อง page-break-before บน "หัวข้อของบล็อก" เอง ไม่ใช่แค่ keepNext บนแถวตาราง (บัญญัติ 2026-09-10 รอบ 3)
ทำตามข้อ 1-2 ข้างบนแล้ว (เพิ่ม cantSplit + keepNext ทุกแถวยกเว้นแถวสุดท้าย) **ยังไม่พอ** — แถวเดี่ยวยังหลุดไปหน้าใหม่แบบไม่มีหัวตารางอยู่ดี เพราะตารางไม่ใช่ท้ายเอกสาร มันมี**ทั้งพารากราฟนำ (เช่น "สรุปข้อ 2") และพารากราฟตาม (คำตอบ + ประโยคปิด) ที่ต้องติดกันเป็นก้อนเดียวกับตารางด้วย** ไม่ใช่แค่ตารางลอยเดี่ยว ๆ — keepNext ที่ตั้งแค่ในตารางไม่ผูกกับพารากราฟนอกตาราง ต้องเชื่อมทั้งบล็อกจริง ๆ:
1. **หาพารากราฟ "หัวข้อของบล็อก" (เช่น label "สรุปข้อ N") ที่อยู่ก่อนตารางทันที แล้วตั้ง `page_break_before = True` บนพารากราฟนั้นเอง** (ตรงนี้ต่างจากข้อ 1 ของรอบสองที่ใช้กับ**ตาราง**ที่ไม่มี label นำหน้า — ถ้ามี label paragraph นำอยู่แล้ว ให้ตั้งบน paragraph จริงตัวนั้นเลย ไม่ต้องสร้าง dummy paragraph ใหม่มาแทรกเหมือนข้อ 1 ของรอบสอง เพราะ label paragraph มีอยู่แล้ว)
2. **ไล่ทุก element ในช่วง [label_paragraph, closing_paragraph) จาก `doc.element.body`โดยตรง (ไม่ใช่ iterate แค่ `doc.paragraphs` เพราะมันข้ามตารางไป) แล้วเช็ค tag**: ถ้าเป็น `w:p` → ตั้ง `keep_with_next=True` บน paragraph นั้น (wrap กลับเป็น `docx.text.paragraph.Paragraph(el, doc)` ก่อน), ถ้าเป็น `w:tbl` → ใส่ `cantSplit` ทุกแถว (เหมือนรอบสอง) — ทำแบบนี้ label→table→answer→closing จะผูกเป็น "ก้อนเดียว" ที่ Word จะดันทั้งก้อนไปหน้าใหม่พร้อมกันถ้าไม่พอดีที่เหลือของหน้าปัจจุบัน แทนที่จะให้ตารางแยกตัวลอยไปเอง
- **เคสจริง**: PRE380 Assessment #3 ทำตามรอบสองแล้ว (cantSplit+keepNext ในตาราง) ส่งไฟล์ไป user ยังเจอแถว "Land Application" หลุดขึ้นหน้า 6 เดี่ยว ๆ เหมือนเดิมทุกประการ — พอเปลี่ยนมาบังคับ page-break-before ที่ label paragraph "สรุปข้อ 2" เอง (ไม่ใช่ dummy paragraph หน้าตาราง) พร้อม chain keepNext ข้าม body element ตั้งแต่ label ถึงก่อนประโยคปิด ถึงแก้ตกจริง
- ใช้เมื่อบล็อกที่ต้องกันไม่ให้แตกหน้า **มี label/พารากราฟนำก่อนตาราง** (ไม่ใช่แค่ตารางลอยเดี่ยวแบบตารางโจทย์ในรอบสอง) — เช่น "สรุปข้อ N" + ตาราง + คำตอบ + ประโยคสรุปที่ต้องอยู่หน้าเดียวกันทั้งหมด

## Human-sounding .docx report (ไม่ใช่ Word Heading style + ไม่มี note/caveat แถม) (บัญญัติ 2026-08-14)
เวลาสร้างรายงาน/การบ้านเป็น `.docx` (ผ่าน HTML → Word COM หรือทางไหนก็ตาม) แล้ว user บ่นว่า "ดูเป็น AI" ทั้งที่แก้คำแล้วหลายรอบ ให้เช็ค**โครงสร้างเอกสาร**ก่อนเช็คคำ — พบว่าตัวที่ทำให้ดู AI ที่สุดไม่ใช่ถ้อยคำ แต่คือโครงสร้าง/ฟีเจอร์การจัดหน้าแบบนี้:

1. **ห้ามใช้ Word Heading style (Heading 1/2/3 ฯลฯ) กับหัวข้อ** — style พวกนี้ทำให้ Word โชว์ลูกศร collapse/expand (กด "dropdown" ยุบ/ขยายได้) หน้าตาเป็นเอกสารวิจัย/รายงานที่ generate มา ไม่ใช่พิมพ์เอง ให้ตั้งหัวข้อเป็น **ตัวหนาธรรมดาบน style ปกติ (Normal)** แทน — ถ้าสร้างผ่าน Word COM (SaveAs จาก HTML) ให้ post-process อีกรอบ: loop ทุก paragraph ที่ `OutlineLevel < 10` (แปลว่าเคยเป็น heading) → set `Range.Style = -1` (wdStyleNormal) + คง `Font.Bold=True` + คง `Font.Size` เดิม + set `OutlineLevel = 10` (wdOutlineLevelBodyText) เพื่อปิด collapse arrow
2. **ตัด paragraph type "หมายเหตุ/note" ที่เป็นแค่ caveat, cross-reference, หรือ recap ซ้ำสิ่งที่พูดไปแล้วออกทั้งพารากราฟ** — ไม่ใช่แค่ปรับคำ นี่คือจุดใหญ่สุดที่ทำให้ดู AI: รายงาน AI ชอบแปะ "หมายเหตุ: ..." / "ตรวจสอบซ้ำด้วย..." / "ดูภาคผนวก..." ต่อท้ายทุก section เพื่อความครบถ้วนทางวิชาการ แต่นักเรียนจริงเขียนจบแล้วก็จบ ไม่วนกลับมาเพิ่ม disclaimer ทุกจุด ถ้าเนื้อหาใน note พูดซ้ำสิ่งที่ประโยคหลักบอกไปแล้ว หรือเป็น caveat ที่ไม่จำเป็นต่อคำตอบ → **ตัดทิ้งทั้งพารากราฟ** ไม่ใช่แค่ทำให้สั้นลง
3. **ห้ามใช้ em dash (—)** ในหัวข้อ/caption — ใช้ `:` หรือเว้นวรรคเฉยๆ แทน
4. **ห้ามใช้เครื่องหมายลบพิเศษ (−, Unicode minus)** — ใช้ `-` (hyphen ธรรมดา) ทั้งในสูตรลบและเลขติดลบ เพราะ − คือสัญลักษณ์ที่ font/copy-paste จาก AI มักติดมา ส่วนคนพิมพ์เองจะกด `-` บนคีย์บอร์ดเสมอ
5. **ลดวงเล็บ () ให้เหลือเฉพาะที่จำเป็นจริง** — วงเล็บที่เป็น unit clarifier ("(พันดอลลาร์)"), English term gloss ("(slope)", "(extrapolation)"), หรือ cross-reference ("(ดูภาคผนวก A)") ให้เอาออกแล้วเรียบเรียงประโยคใหม่ให้ข้อมูลนั้นไหลอยู่ในประโยคแทน — **เก็บไว้เฉพาะ** วงเล็บที่ทำหน้าที่ระบุค่าจริงติดกับสัญลักษณ์ เช่น "ความชัน (b₁ = 1.2667):" เพราะเป็นการ label ค่าตัวแปร ไม่ใช่ aside
6. **เลขหัวข้อย่อยแบบ decimal (1.1/1.2/1.3, 2.1/2.2) ไม่ต้องมีคำนำหน้าซ้ำ** เช่น "งานที่ 1 — " เพราะเลขบอกลำดับอยู่แล้ว การมีทั้งคำนำหน้าซ้ำ+เลขหัวข้อ เป็นการจัดรูปแบบเกินจำเป็นที่เอกสาร generate ชอบทำ
7. **เช็คระยะห่างระหว่างหัวข้อ/ตาราง (`SpaceBefore`/`SpaceAfter`)** หลังแปลงจาก HTML — CSS `margin-top` ของ heading (เช่น 28px) มักกลายเป็น space-before ที่เว่อร์เกินไปในเวอร์ชัน docx ทำให้ดูเป็นเอกสารจัดหน้าอัตโนมัติ ให้ normalize ทุก paragraph นอกตาราง (`SpaceBefore=12/SpaceAfter=4` สำหรับหัวข้อ, `4/4` สำหรับ body) แต่**ห้ามแตะ paragraph ที่ font เป็น monospace (เช่น Consolas)** เพราะเป็น code block ที่ต้องบรรทัดชิดกันตามปกติ ไม่งั้นโค้ดจะมีช่องว่างแทรกทุกบรรทัดจนอ่านไม่รู้เรื่อง

- **เหตุผล/เคสจริง (2026-08-14):** ทำการบ้าน CPE 342 OLS regression report — ผ่านการปรับคำ/ลด AI-tell ทางภาษาไปหลายรอบแล้ว (Opus แปล, ลด hedge, ลดวงเล็บ) user ยังบอกว่า "ยังดู AI อยู่" จนสุดท้าย user แก้ .docx เอง 1 หน้า + 1 ข้อเป็นตัวอย่าง แล้วให้ทำตามทั้งฉบับ — พบว่าสิ่งที่ user ตัดออกจริงๆ คือ**ทุก paragraph class="note"** (caveat/cross-check/recap ท้าย section) ตัดทิ้งทั้งพารากราฟ ไม่ใช่แค่ปรับคำ, ตัดคำนำหน้า "งานที่ N —" ออกเปลี่ยนเป็นเลข decimal, ตัด em dash และวงเล็บ aside เกือบหมด — และเมื่อลองใช้ Word Heading style ตอนแรก user บ่นว่า "ไม่ต้องเอาแบบกด dropdown ได้" (หมายถึงลูกศร collapse ของ Word heading outline)
- **สรุปบทเรียน:** anti-AI-tell ระดับคำ (em dash, hedge, vocab) แก้ได้แต่ไม่พอถ้าโครงสร้างเอกสารยังมี "ส่วนเกิน" ที่มีแต่ AI ชอบใส่ (note ซ้ำซ้อน, heading style ที่ generate มา, วงเล็บ gloss) — ให้เช็คโครงสร้างเอกสารทั้งฉบับก่อน ไม่ใช่ไล่คำทีละประโยค
- ใช้กับทุก project ที่สร้างรายงาน/เอกสาร .docx ให้ user ที่กังวลเรื่อง AI-detection (การบ้าน, งานเขียนที่ต้องส่งเป็นของตัวเอง) — ไม่ใช่แค่ thai-docx skill

## รอบสอง: ตัวอย่างแก้จริงจาก user (CPE 342 Lab4 regression report, บัญญัติ 2026-08-25)
เคสนี้ user ไม่ได้บ่นว่า "ยังดู AI" ตรงๆ แต่ขอให้ไปดูว่าแก้อะไรบ้างเพื่อเอามาปรับสกิล — diff ระหว่างฉบับที่ส่งกับฉบับที่ user แก้เอง เจอ pattern เพิ่มที่ชัดเจน:
