## Thai writing anti-AI-tell rules (บัญญัติ 2026-08-13, ขยายเพิ่ม 2026-08-13 จาก Wikipedia:Signs_of_AI_writing + web research)
เวลา draft เนื้อหาภาษาไทย (การบ้าน, เรียงความ, รายงาน, บทความ, แชท) ให้เลี่ยง pattern เหล่านี้ที่เป็น signature ของข้อความ AI-generated ภาษาไทย:
- **คำเชื่อม essay-formal เปิดย่อหน้า**: ห้ามใช้ "อย่างไรก็ตาม / นอกจากนี้ / ในขณะเดียวกัน / ทั้งนี้ / ดังนั้น" เปิดย่อหน้าเกิน 1 ครั้งต่อทั้งชิ้น และห้าม rotate คำเชื่อมกลุ่มนี้ไม่ซ้ำกันทุกย่อหน้า
- **list สมมาตร 3 ข้อ**: ห้ามยกตัวอย่างทีละ 3 ข้อที่โครงประโยคขนานกันยาวเท่ากันเสมอ — ให้ยก 2 หรือ 4 บ้าง ยาวไม่เท่ากัน และเลี่ยงสูตรเปิด "ไม่ว่าจะเป็น... หรือ..."
- **ประโยคจบแบบ restate ครบ**: ห้ามขึ้นจบด้วย "สรุปได้ว่า / กล่าวโดยสรุป / ท้ายที่สุดแล้ว" แล้ววนทวนทุกประเด็น — ให้จบด้วยความเห็นส่วนตัว/detail คมๆ สั้นกว่าที่อยากจบเสมอ
- **ความยาวประโยคสม่ำเสมอเกินไป + ไม่มี detail เฉพาะตัว**: ต้องมีประโยคสั้นกระแทกแทรกบ้าง สลับกับยาว และงานเล่า/เรียงความต้องมี detail เฉพาะเจาะจงอย่างน้อย 1 จุด (ชื่อ สถานที่ เหตุการณ์ ตัวเลขจริง) ถ้าไม่รู้ให้ถาม user แทนเขียน generic
- **Register**: ต้องรู้ว่ากำลังเขียนแบบไหน (การบ้าน/วิชาการ/บทความ/แชท/สร้างสรรค์) แล้วปรับให้เข้ากับ register นั้น ห้าม default เป็นโทน essay-formal ทุกครั้ง — แชทควรมี particle (อ่ะ/แหละ/เลย/555) ละประธานได้, การบ้านนักเรียนควรมีสรรพนาม "ผม/หนู" และประสบการณ์ตรง
- **nominalization แปลอังกฤษ**: เลี่ยง "มีความสามารถในการ X", "อย่างมีประสิทธิภาพ/อย่างมีนัยสำคัญ" ให้ใช้กริยาไทยตรงๆ แทน (ยกเว้นงานวิชาการแท้ที่ต้องใช้ศัพท์บัญญัติ)
- **หลีกเลี่ยง copula "เป็น/คือ"**: AI ชอบแทนที่ประโยคบอกเล่าตรงๆ ด้วย "ทำหน้าที่เป็น", "ถือเป็น", "สะท้อนให้เห็นถึง", "นับว่าเป็น" — ถ้าพูดตรงๆ ว่า "X คือ Y" ได้ก็พูดตรงๆ ไป ไม่ต้องอ้อม
- **negative-parallelism "ไม่ใช่แค่ X แต่ยังเป็น/แต่ยังรวมถึง Y"**: เป็นแม่แบบประโยคที่ AI ใช้บ่อยเกินจริงเพื่อสร้างมิติปลอมๆ ให้ประเด็นง่ายๆ — ใช้ได้นานๆครั้งจริงๆ ที่มี contrast ชัดเจน ห้ามใช้เป็นโครงประโยคหลักซ้ำๆ ในชิ้นเดียว
- **การอ้างอิงลอยๆ ไม่มีแหล่งจริง**: เลี่ยง "ผู้เชี่ยวชาญระบุว่า", "มีการศึกษาพบว่า", "จากสถิติชี้ให้เห็นว่า" โดยไม่มีชื่อ/แหล่งที่มาจริงรองรับ — ถ้าไม่มีแหล่งจริงให้พูดเป็นความเห็นตรงๆ ("ผมว่า...") แทนสร้าง authority ปลอม
- **สูตรจบแบบ hedge-แล้ว-เน้น**: เลี่ยงโครง "แม้จะมี [จุดดี] แต่ก็ยังคงเผชิญกับความท้าทาย/ปัญหาอยู่" ปิดท้ายทุกย่อหน้า/ทุกชิ้นงาน — เป็นสูตร AI สร้างความสมดุลปลอมๆ ไม่ใช่การวิเคราะห์จริง
- **สลับคำพ้องความหมายถี่เกินธรรมชาติ (elegant variation)**: AI มักเลี่ยงคำซ้ำด้วยการเรียกสิ่งเดียวกัน 2-3 ชื่อสลับกันในย่อหน้าเดียว (เช่นเรียก "หมา" แล้วเปลี่ยนเป็น "สุนัขตัวนั้น" แล้วเปลี่ยนเป็น "เพื่อนสี่ขา" ในย่อหน้าเดียว) — คนเขียนจริงเรียกซ้ำคำเดิมได้ตามธรรมชาติ ไม่ต้องเลี่ยง
- **โทนโปรโมท/โบรชัวร์ท่องเที่ยวในบริบทกลาง**: เลี่ยงคำบวกเกินจริงพร่ำเพรื่อ เช่น "งดงาม", "เต็มไปด้วยเสน่ห์", "มีชีวิตชีวา", "น่าประทับใจอย่างยิ่ง" ในเนื้อหาที่ไม่ได้ขอรีวิว/โฆษณา — โดยเฉพาะเวลาบรรยายสถานที่/สิ่งของธรรมดาๆ
- **formatting ล้นเกินบริบท**: bold ทั้งย่อหน้า, ใช้ emoji คั่นหัวข้อพร่ำเพรื่อ, เส้นคั่น (---) ก่อนหัวข้อย่อยที่ไม่จำเป็น, สร้างตารางในแชท/การบ้านทั้งที่พูดเป็นข้อความธรรมดาก็พอ — ใช้ formatting หนักเฉพาะงานที่ user ขอเป็นเอกสาร/สไลด์จริงๆ
- **เนียนสมบูรณ์แบบเกินไป (zero human noise)**: งานคนจริง (โดยเฉพาะแชท/เรียงความเล่าประสบการณ์) มักมีจังหวะพูดติดขัด เปลี่ยนใจกลางประโยค ใช้คำเฉพาะตัวบ้าง — อย่าเกลาทุกประโยคให้เรียบร้อยสมบูรณ์แบบเท่ากันหมด ปล่อยให้มีเสียงพูดจริงบ้างตาม register
- **คำศัพท์ไทยที่ AI ใช้เกินจำเป็น (Thai GPT-isms)**: "เจาะลึก" (delve), "พลิกโฉม"/"เปลี่ยนโฉม" (revolutionize เกินบริบท), "ยกระดับ" (elevate เกินบริบท), "ตอกย้ำ" (underscore), "ตกผลึก" (ใช้นอกบริบทสรุปความคิดจริงๆ), "หลากหลายมิติ"/"รอบด้าน" (multifaceted filler), "โอบรับ" (embrace แปลตรงตัว), "องค์รวม" ใช้พร่ำเพรื่อ — ถ้าจะใช้ต้องใช้เพราะความหมายตรงจริงๆ ไม่ใช่เพราะฟังดูหรู
- **อธิบายเหตุผลแบบตำราเนียนเกิน (over-explained textbook reasoning)** (เพิ่ม 2026-09-08): AI ชอบแทรกคำอธิบายทฤษฎี generic ต่อท้ายทุกขั้นตอนแม้ไม่มีใครถาม เช่น "เพราะ Random Forest คือการเฉลี่ยผลจากต้นไม้หลายต้น ที่สุ่มตัวอย่างข้อมูลและตัวแปรต่างกัน จึงลดความแปรปรวนของโมเดลเดี่ยวลงได้" ทั้งที่รายงานแค่บอกว่าตั้งค่าอะไรทำไมก็พอ — จุดสังเกต: ถ้าตัดประโยคนั้นทิ้งแล้วเนื้อหาไม่เสียหาย นั่นคือ filler ตำรา ให้ตัดสั้นลงเหลือแค่ผลที่สังเกตได้จริงจากงานที่ทำเอง ไม่ใช่ derive จากทฤษฎีให้ครบเป๊ะเหมือนสอนหนังสือ
- **overclaim เกินหลักฐาน (evidence overclaim)** (เพิ่ม 2026-09-08): AI ชอบใช้คำสรุปที่ฟังดูมั่นใจ/เด็ดขาดกว่าที่ข้อมูลพิสูจน์ได้จริง เช่น เรียก feature importance สูงว่าเป็น "ตัวตัดสินหลัก" (ทั้งที่บอกได้แค่ว่าโมเดลใช้ตัวแปรนั้นทำนายเยอะ ไม่ใช่ความสัมพันธ์เชิงเหตุผล), เรียก accuracy/recall ที่สวนทางกันว่า "ขัดกันเอง" (ทั้งที่เป็นผลจาก class imbalance ไม่ใช่ความขัดแย้งโดยธรรมชาติ), หรือสรุปว่าผลต่าง "จึงมาจาก" สาเหตุหนึ่งทั้งที่หลักฐานแค่บ่งชี้ความเป็นไปได้ (เช่น AUC ใกล้กันแต่ recall ต่างกันมาก) — แก้โดยลดระดับความมั่นใจของคำให้ตรงกับหลักฐานจริง ("มีแนวโน้ม", "เป็นไปได้ว่า", "ให้ความสำคัญมากที่สุด" แทน "ตัดสินหลัก"/"พิสูจน์แล้วว่า")
- **แต่งเหตุผล/use case ที่ข้อมูลไม่ได้บอกไว้ (invented justification)** (เพิ่ม 2026-09-08): AI ชอบเติม motivation ให้ตัวเลขที่ไม่มีมูลจากข้อมูลจริง เช่นบอกว่าการเลือกโมเดลนี้ "ไม่ให้พลาดคนเก่ง" ทั้งที่ label ในข้อมูลมีแค่ Admit/ไม่ Admit ไม่ได้แปลว่า "เก่ง" โดยตรง — ยึดกับสิ่งที่ตัวแปร/label บอกจริงๆ เท่านั้น ห้ามต่อเติม narrative หรือ interpretation ที่ฟังดูสมเหตุสมผลแต่ไม่มีอะไรรองรับ
- **ปิดทุกช่องเหตุผลจนสมบูรณ์เกิน (closing every logical gap)** (เพิ่ม 2026-09-08 รอบ 2): AI มักเขียนสายโซ่เหตุผลแบบ "A จึงทำให้ B เพราะ C ส่งผลให้ D" ที่ปิดทุกช่องไม่เหลือที่ว่าง ทั้งที่ยังไม่มีหลักฐานรองรับครบทุกขั้น (เช่นสรุปว่าโมเดล "เรียนรู้ที่จะทายว่าไม่รับไว้ก่อนเกือบตลอด" ทั้งที่มีแค่ accuracy/recall ไม่มี confusion matrix มายืนยันพฤติกรรมโมเดลจริง) — คนเขียนรายงานจริงมักอธิบายจากสิ่งที่สังเกตได้ตรงๆ ไม่ปิดทุกช่องเหมือนตอบข้อสอบ แก้โดยเปลี่ยนจากอธิบายเหตุ-ผลครบวงจรเป็นบอกผลที่สังเกตได้จริงพร้อม hedge แทน เช่นจาก "A จึงทำให้ B เพราะ C" เหลือแค่ "ผลที่ได้คือ B ซึ่งน่าจะเกี่ยวข้องกับ C"
- **คำเชื่อมเหตุ-ผลที่ควรเลี่ยงเพราะฟังมั่นใจเกินหลักฐาน**: "แสดงว่า", "จึงทำให้", "เป็นเพราะ", "เหมาะกับงาน...เสมอ" — ใช้ "จากผลการทดลองนี้", "พบว่า", "ค่า...สูงกว่า/ต่ำกว่า", "อาจเกิดจาก", "เป็นไปได้ว่า" แทน เพื่อให้ระดับความมั่นใจของประโยคตรงกับหลักฐานที่มีจริง (ยกเว้นมีหลักฐานรองรับตรงๆ ครบจริงถึงใช้คำมั่นใจเต็มที่ได้)
- **โครง "เนื่องจาก...จึง..." สมบูรณ์เกินแม้เนื้อหาถูกต้อง** (เพิ่ม 2026-09-08 รอบ 3): แม้ประโยคจะไม่ผิดข้อเท็จจริงเลย โครงประโยคทางการแบบ "เนื่องจาก A ... จึง B" ที่เป๊ะทุกจุดก็ยังอ่านเหมือน AI ได้ (คนละปัญหากับข้อ "ปิดทุกช่องเหตุผล" ด้านบนซึ่งเป็นเรื่อง confidence เกินหลักฐาน — อันนี้แม้เนื้อหาถูก 100% โครงประโยคเองก็ยังดูเป็นทางการ/AI) — แก้โดยสลับเป็นโครงหลวมกว่า เช่นจาก "เนื่องจาก A มาก B จึงอาจสูงได้" เป็น "ในข้อมูลชุดนี้ A มาก ทำให้ B อาจดูสูง แม้ C จะต่ำ" (บอกสภาพที่สังเกตแล้ววางเคียงกัน ไม่ต้อง frame เป็นเหตุ-ผลทางการทุกประโยค)
- **เสนอ future work แบบทางการ/กว้างเกินไป (generic future-work suggestion)** (เพิ่ม 2026-09-08 รอบ 3): AI ชอบปิดท้ายด้วยข้อเสนอแนะทำงานต่อแบบเป็นทางการและกว้าง เช่น "อาจใช้วิธีจัดการ class imbalance เพิ่มเติม" ทั้งที่นักศึกษาจริงมักเขียนสิ่งที่ตัวเองจะลองทำต่อแบบเจาะจงกว่านั้น เช่น "อาจทดลองเปลี่ยน threshold ดูว่า recall ดีขึ้นไหม" — ให้เจาะจงและทำได้จริงในโจทย์นี้ ไม่ใช่คำแนะนำกว้างๆ แบบตำรา/บทสรุปงานวิจัย
- **ใส่ตัวเลขจริงแทนคำคุณศัพท์กว้างๆ ในบทสรุป** (เพิ่ม 2026-09-08 รอบ 3): ประโยคสรุปที่ใส่เลขเจาะจง (เช่น "recall ประมาณ 0.89") อ่านน่าเชื่อและเป็นมนุษย์กว่าประโยคกว้างๆ ("recall ยังอยู่ในระดับสูง") เพราะเลขจริงบอกว่าคนเขียนอ่านผลตัวเองมาจริง — ถ้ามีตัวเลขอยู่ในมืออยู่แล้ว (จากตาราง/ผลทดลองที่ทำเอง) ให้ใส่แทนคำคุณศัพท์เสมอ อย่าสรุปลอยๆ ทั้งที่มีเลขจริงให้อ้างอิงได้
- **ตัด modifier/วลีสั้นที่ฟังเหมือนถูกตัดมาจากคำอธิบายยาว** (เพิ่ม 2026-09-08 รอบ 4): AI บางทีย่อประโยคจนสั้นเกินจริง เช่น "เพื่อลดจำนวนคอลัมน์ที่ได้" (ลดคอลัมน์อะไร ที่ได้จากไหน ไม่ชัด) — คนเขียนจริงจะระบุที่มาของสิ่งที่พูดถึงให้ครบ เช่น "เพื่อลดจำนวนคอลัมน์จาก one-hot encoding" แก้โดยเช็คว่าประโยคสั้นๆ ที่ตัด subject/ที่มาออกไปยังเข้าใจได้ครบไหมถ้าอ่านแยกจากบริบท ถ้าไม่ครบให้เติมกลับ
- **register ปนกันภายในเอกสารเดียว ต้องเกลาให้สม่ำเสมอ ไม่ใช่ตัดภาษาพูดออกให้หมด** (เพิ่ม 2026-09-08 รอบ 4): ภาษาพูดกึ่งวิชาการ (เช่น "เช็ค", "ถ้าดู...เฉย ๆ") ช่วยให้ไม่ดู AI แต่ถ้าใช้ระดับความเป็นทางการสวนกันในคำใกล้กัน (เอกสารใช้ "ตรวจสอบ" ทุกที่ยกเว้นจุดหนึ่งที่หลุดมาเป็น "เช็ค") จะดูเหมือนแก้ไม่ครบมากกว่าดูเป็น AI — เกลาให้ทั้งเอกสารอยู่ใน register เดียวกันหลังตัดสินใจ register แล้ว (ตามกฎ "Register" ด้านบน) ไม่ใช่ไล่ตัดคำภาษาพูดออกทุกจุดจนกลายเป็นทางการทั้งหมดอีกที
- **คำซ้ำเป็น anchor เชื่อมประโยคที่ AI ชอบใช้แต่ซ้ำเกินในระยะสั้น (repeated discourse-anchor phrase)** (เพิ่ม 2026-09-08 รอบ 5): AI ชอบใช้วลีเชื่อมแบบเดิมซ้ำ (เช่น "จากผลที่ได้") เปิดหลายประโยคติดกันในย่อหน้าสั้นๆ เพื่อ signal ว่ากำลังสรุป — คนเขียนจริงจะไม่ทวนวลีเดิมถ้าไม่จำเป็น ตัดออกเมื่อประโยคเข้าใจได้อยู่แล้วโดยไม่มี anchor นั้น (ไม่ใช่แค่คำเชื่อมเปิดย่อหน้าตามข้อแรกของสกิลนี้ — อันนี้คือวลีอะไรก็ได้ที่ซ้ำตัวเองในช่วงสั้นๆ)
- **คำที่แปลตรงตัวแต่ไม่เข้าปาก แม้ความหมายถูก (awkward literal collocation)** (เพิ่ม 2026-09-08 รอบ 5): บางคำแปลตรงจากอังกฤษแล้วความหมายถูกเป๊ะแต่คนไทยไม่พูดแบบนั้น เช่น "อ้างอิงผลจาก" (refer to the result) ที่ควรเป็น "พึ่งผล/อิงผล" — เช็คว่าคำกริยา+วัตถุที่จับคู่กันฟังดู idiomatic จริงไหม ไม่ใช่แค่ถูกไวยากรณ์
- **คำซ้ำภายในประโยคเดียว (เช่น ศัพท์เทคนิคซ้ำตัวเองเป็น object ของ preposition ที่มัน derive มา)** (เพิ่ม 2026-09-08 รอบ 6): เช่น "ลดจำนวนคอลัมน์จาก one-hot encoding" ที่ one-hot encoding เพิ่งถูกพูดถึงไปหมาดๆ ในประโยคเดียวกัน — คนเขียนจริงจะตัดคำซ้ำที่ infer ได้จากบริบทอยู่แล้วทิ้ง เหลือแค่ "ลดจำนวนคอลัมน์ที่สร้างขึ้น" เช็คทุกประโยคว่ามีคำ/ศัพท์เทคนิคซ้ำตัวเองโดยไม่จำเป็นไหม
- **คำ hedge ระดับภาษาพูดที่ปนอยู่ในประโยคทางการ (เช่น "แค่", "มากแค่")** (เพิ่ม 2026-09-08 รอบ 6): "ต่ำมากแค่ 0.126" มีทั้ง "มาก" และ "แค่" ซ้อนกันฟังเป็นภาษาพูด — ถ้าประโยครอบข้างเป็น register ทางการ ให้ใช้คำนามธรรมดาแทน เช่น "ต่ำเพียง 0.126" ไม่ใช่ signal ของ AI-tell โดยตรง แต่เป็นจุดที่ทำให้ register ไม่สม่ำเสมอ (เกี่ยวเนื่องกับข้อ "register ปนกัน" รอบ 4)
- **ประโยคสองท่อนที่มีวัตถุร่วม (shared object) แต่เขียนซ้ำชื่อวัตถุทั้งสองท่อน** (เพิ่ม 2026-09-08 รอบ 6): เช่น "รองลงมาคือ feature B ค่า feature importance ของ feature A และ feature B รวมกัน..." — ท่อนแรกเพิ่งพูดถึง feature A/feature B แยกกัน ท่อนสองพูดถึงทั้งคู่รวมกันแต่เขียนชื่อซ้ำทั้งสองตัวอีกที ทำให้อ่านเหมือนคำตกหรือ AI ต่อประโยคแบบไม่ตัดคำซ้ำ — แก้โดยใช้คำแทน ("สองตัวแปรนี้") ในท่อนที่สอง
- **จุดหยุดพักในหัวเรื่องรายงานให้ไม่มีวรรคก่อนคำเชื่อม "คือ" เมื่อประโยคสั้นตรงไปตรงมา** (เพิ่ม 2026-09-08 รอบ 6): "จุดแยกแรกสุดของต้นไม้ คือคะแนน feature A" มีวรรคก่อน "คือ" ทั้งที่ไม่มีจังหวะหยุดพักทางความหมายจริง — วรรคที่ไม่มีเหตุผลทางไวยากรณ์/ความหมายรองรับเป็นสัญญาณของประโยคที่ประกอบมาไม่เนียน (ไม่ใช่ AI-tell เนื้อหา แต่เป็น mechanical fix ระดับ punctuation ที่ควรเช็คด้วยเหมือนกัน)
- **จุดตัดสิ้นสุดการไล่แก้ (diminishing returns signal)** (เพิ่ม 2026-09-08 รอบ 6): เมื่อ user เริ่มเสนอทางเลือก "เดิม vs แก้" หลายจุดพร้อม comment "ถ้าอยากเป็นทางการก็แก้ได้ แต่ถ้าไม่อยากดู AI เก็บของเดิมไว้ก็ได้" — นั่นคือสัญญาณว่าเข้าเขต stylistic preference ที่ไม่มีคำตอบถูก/ผิดแล้ว ไม่ใช่ AI-tell จริงอีกต่อไป ให้ทำแค่ list ที่ user บอกว่า "แก้จริงๆก่อนส่ง" เท่านั้น ไม่ต้องไล่ทำรายการที่เหลือทั้งหมด แม้จะฟังดูดีขึ้นก็ตาม — เกลามากเกินจุดนี้มีความเสี่ยงย้อนกลับไปดูเป็น AI ตามที่ user เตือนไว้ตรงๆ (over-polish โดยตัด human noise ที่เหลือออกจนหมด)
- **ประโยคเดียวไล่อธิบายครบทุกกรณีย่อย (single-sentence case-enumeration)** (เพิ่ม 2026-09-10 รอบ 7): AI ชอบยัดทุกกรณีย่อยไว้ในประโยคเดียวต่อกันด้วย "...ส่วน X ก็ Y... และ Z ก็ W..." เช่น "ใช้ ia นี้กับกระแสเงินสดที่จ่ายเป็นรายปี... ส่วน Option A จ่าย opex ทุกครึ่งปีตรงกับรอบทบต้น ใช้ i = 5% ได้เลย และ Option B จ่าย opex ทุกไตรมาส ต้องแปลงเป็นอัตรารายไตรมาส" — คนเขียนจริงจะแยกเป็นข้อเท็จจริงสั้นๆ ทีละเส้น ไม่ไล่ enumerate ทุกกรณีในประโยคเดียวยาว
- **วลี hedge-flag แบบ "อีกจุดที่ต้องระวัง/ข้อควรระวังคือ" เปิดย่อหน้า** (เพิ่ม 2026-09-10 รอบ 7): เป็นสูตร AI ที่ชอบประกาศล่วงหน้าว่ากำลังจะเตือนอะไร ก่อนอธิบายเนื้อหาจริง — คนเขียนรายงานจริงพูดข้อเท็จจริง/วิธีทำตรงๆ ไม่ต้อง flag ตัวเองว่า "นี่คือจุดที่ต้องระวังนะ" ตัดวลีนำแบบนี้ออก แล้วเข้าเนื้อหาตรงๆ
- **แต่งเหตุผลอธิบายผลต่างระหว่างวิธีโดยไม่มีอะไรพิสูจน์ (unproven causal narrative for a discrepancy)** (เพิ่ม 2026-09-10 รอบ 7): เจอในย่อหน้าสรุปที่อธิบายว่าทำไมสองวิธีคำนวณให้คำตอบต่างกัน เช่น "ทำให้ผลตอบแทนของเงินลงทุนก้อนใหญ่ใน Option A ดูดีขึ้น เพราะรายได้ที่เกิดจากมันถูกทบต้นด้วยอัตรา reinvestment ที่สูงถึง 15%" — ฟังดูสมเหตุสมผลแต่ผิดข้อเท็จจริง (รายได้เป็นรายได้ร่วมของทุกทางเลือก ไม่ใช่ "รายได้ที่เกิดจาก Option A") และเป็นคำอธิบายที่ผู้เขียนไม่ได้พิสูจน์จริง แค่ผลลัพธ์ต่างกันก็ปะติดปะต่อเหตุผลให้ฟังดูสมบูรณ์ — แก้โดยรายงานแค่ตัวเลขผลลัพธ์ของทั้งสองวิธีเทียบกันตรงๆ ("วิธี A ใช้อัตรา X ได้ผล P, วิธี B ใช้อัตรา Y ได้ผล Q") ไม่ต้องแต่งเหตุผลว่า "ทำไม" ถ้าไม่ได้ derive มาเป๊ะจากตัวเลขจริง — เกี่ยวเนื่องกับ "ปิดทุกช่องเหตุผล" (รอบ 2) แต่ต่างกันตรงนี้เนื้อหาผิดจริง ไม่ใช่แค่มั่นใจเกินหลักฐาน
- **โครง "X จึงคุ้มค่า เลือก X แทน Y" ซ้ำรูปแบบเดิมทุกจุดตัดสินใจ** (เพิ่ม 2026-09-10 รอบ 7): เวลาต้องสรุปผลเทียบค่าหลายจุด (เช่น incremental ROR หลายคู่) อย่าพิมพ์ประโยคสรุปด้วยแม่แบบเดิมซ้ำทุกครั้ง ("[ค่า] สูงกว่า [เกณฑ์] [ระดับ] การลงทุนเพิ่มใน X จึงคุ้มค่า เลือก X แทน Y") — ใช้รูปแบบสั้นตรงสูตร "X = ค่า > เกณฑ์ = ค่า จึงเลือก X" แทน อ่านเหมือนคนคำนวณจริงมากกว่าเล่าเหตุผลซ้ำทุกรอบ
- **case-study บทเรียนเรื่องความถูกต้อง ไม่ใช่แค่โทนภาษา**: ระวังไว้ด้วยว่าบาง pattern ที่ดู AI-tell ทางโทนเสียง (อธิบายเหตุผลเกิน) พ่วงมากับ **ความผิดพลาดทางเนื้อหาจริง** ได้ เช่นประโยค "Option B แพงกว่าเพราะไม่มี first cost มาช่วยลดภาระรวม" ผิดทั้งตรรกะ (first cost คือต้นทุน ไม่ใช่สิ่งที่ช่วยลดภาระ) และผิดทั้งโทน — เวลาเจอประโยคที่ "ฟังดู AI" ให้เช็คความถูกต้องทางเนื้อหาควบคู่ไปด้วยเสมอ ไม่ใช่แก้แค่คำให้ดูเป็นคนเขียนแล้วปล่อยเนื้อหาผิดผ่านไป
- **premise ที่ solver เติมเองโดยโจทย์ไม่ได้ให้มา (self-invented premise)** (เพิ่ม 2026-09-10 รอบ 7, ไม่ใช่แค่ AI-tell แต่เป็น correctness gap): เวลาทำโจทย์เศรษฐศาสตร์วิศวกรรม/ROR ที่ต้องเรียงทางเลือกจาก first cost น้อยไปมากแล้วเทียบทีละคู่ ห้ามเติม "เทียบกับไม่ทำอะไรเลย (do nothing)" ให้ทางเลือกที่ first cost ต่ำสุดโดยอัตโนมัติ ถ้าโจทย์บอกว่าต้องเลือกหนึ่งในทางเลือกที่ให้มาจริง (mandatory choice, ไม่มีตัวเลือก "ไม่ทำ") — ต้องเช็คเงื่อนไขโจทย์ก่อนเสมอว่ามี do-nothing เป็นทางเลือกจริงไหม แล้วเริ่ม incremental analysis จากทางเลือกที่ first cost ต่ำสุดโดยตรงถ้าไม่มี
- **คำอธิบาย causal ที่ตัดปัจจัยอื่นออกจนฟันธงเกิน แม้เนื้อหาไม่ผิด** (เพิ่ม 2026-09-10 รอบ 8): เช่น "Option B มี PW ต่ำที่สุด เนื่องจากมีค่าใช้จ่ายดำเนินการทุกไตรมาส" — ที่จริง PW ต่ำเกิดจากมูลค่ารวมของกระแสเงินสดทั้งหมด ไม่ใช่แค่ "ความถี่การจ่าย" อย่างเดียว ประโยคที่ใช้ "เนื่องจาก" ผูกกับปัจจัยเดียวแบบนี้ทำให้ดูฟันธงเกินสิ่งที่พิสูจน์จริง — แก้โดยเปลี่ยนจาก "เนื่องจาก X" เป็น "จาก X" (บรรยายปัจจัยที่เห็น ไม่ใช่กล่าวอ้างว่าเป็นสาเหตุเดียว)
- **คำลงท้าย/บอก emphasis ที่ไม่มีข้อมูลรองรับต่อท้ายตัวเลขในตาราง (unnecessary table commentary)** (เพิ่ม 2026-09-10 รอบ 8): เช่นในตารางสรุปใส่ "ผ่าน (ห่างกันน้อยมาก)" ทั้งที่ตัวเลขในคอลัมน์ข้างๆ (10.70% vs MARR 10.25%) บอกอยู่แล้วว่าห่างกันแค่ไหน — คนอ่านตารางเห็นตัวเลขเองได้ ไม่ต้องใส่ comment ซ้ำในเซลล์ ตัดคำขยายที่ไม่ใช่ข้อมูลใหม่ออกจากตาราง
- **ประโยคสรุปท้ายที่พ่วง "เนื่องจาก...ซึ่งยัง..." ยาวเกินจำเป็นทั้งที่ตัวเลขอยู่ในเนื้อหาก่อนหน้าแล้ว** (เพิ่ม 2026-09-10 รอบ 8): ประโยคปิดท้ายที่ทวนตัวเลข+เหตุผลซ้ำทุกจุด (ทั้งที่เพิ่งอธิบายไปในย่อหน้าก่อนหน้า) อ่านเหมือนรายงาน AI ที่พยายาม "สรุปให้ครบ" — ตัดคำเชื่อมส่วนเกิน ("เนื่องจาก...เท่ากับ...ซึ่งยังสูงกว่า") ให้เหลือโครงสั้น "X เลือก A ขณะที่ Y เลือก B เพราะ [ตัวเลข] สูงกว่า [เกณฑ์]" พอ
- **โครงประโยคขึ้นต้นแบบทางการ "เนื่องจาก A จึงไม่พิจารณา B และเริ่ม C" ที่ตัด "จริง" ปิดท้ายออก** (เพิ่ม 2026-09-10 รอบ 8): เวอร์ชันก่อนหน้ามีคำลงท้ายกันเอง เช่น "...วิธีใดวิธีหนึ่งใน 3 วิธีนี้จริง" ซึ่งฟังดูพูดกันเองเกินไปเมื่อปนกับโครงประโยคทางการรอบข้าง (register ไม่สม่ำเสมอ ตามข้อรอบ 4) — ตัดคำลงท้ายกันเองแบบนี้ออกเวลาอยู่ในย่อหน้าที่เหลือเป็นทางการทั้งหมด ให้ทั้งประโยคอยู่ใน register เดียว
- เหตุผล: pattern ชุดแรก (em dash / "" / คำเชื่อมเปิดย่อหน้า) จับได้แค่ระดับเครื่องหมาย/คำ แต่ชุดขยายนี้มาจากการวิเคราะห์ pattern โครงสร้าง/วาทศิลป์ที่ Wikipedia รวบรวมไว้เป็นระบบ (Wikipedia:Signs of AI writing) แล้วแปล/ปรับให้ตรงกับภาษาไทย — ครอบคลุมกว้างกว่าการดักแค่คำ, คนอ่านที่ชินกับข้อความ AI จับ pattern เชิงโครงสร้างเหล่านี้ได้ง่ายพอกันหรือง่ายกว่าคำเดี่ยวๆ ด้วยซ้ำ
- ใช้กับ: ทุก project ทุกครั้งที่ร่างข้อความเป็นภาษาไทย — รายละเอียดเต็ม+ตัวอย่าง before/after อยู่ใน ไฟล์ memory ของคุณเอง

## Draft-critique-revise workflow (บัญญัติ 2026-09-04, adapted from blader/humanizer)
เดิม skill นี้ใช้แบบ single-pass — เพิ่มขั้น critique/revise แยกเป็น **บังคับ** สำหรับงานที่ความนิ่ง/น่าเชื่อถือสำคัญ (การบ้าน/รายงาน/บทความ/เอกสารที่จะส่ง/โพสต์ให้คนอื่นเห็น) — **ไม่ใช่ทางเลือก** สำหรับงานกลุ่มนี้ ยกเว้นแชตสั้นๆ/ตอบปกติที่ single-pass พอ:
1. **Draft**: เขียนโดยไม่ยึดโครงตายตัว เนื้อหา/ข้อเท็จจริงมาก่อน — แต่ **register ต้องเลือกไว้ตั้งแต่ขั้นนี้** (ตามกฎ "Register" ด้านบน) ค่อยเกลาแค่สำนวน/คำศัพท์ทีหลัง
2. **Critique**: เทียบร่างกับ checklist ด้านบนทีละข้อ + เทียบกับข้อเท็จจริงต้นทาง (กันความหมายเพี้ยน) จด flag เฉพาะจุดที่ชน
3. **Revise**: แก้เฉพาะจุดที่ flag ไม่ rewrite ทั้งชิ้นใหม่
- แชตสั้น/ตอบปกติในบทสนทนา → single-pass เดิมพอ ไม่ต้องแยกขั้น

## Humanize existing text (บัญญัติ 2026-09-04)
เมื่อ user ขอ "humanize ข้อความนี้ / แก้ให้ไม่เหมือน AI เขียน" กับ**ข้อความ/ไฟล์ที่มีอยู่แล้ว**:
1. อ่านต้นฉบับเต็ม เก็บ meaning/claims/รายละเอียดทั้งหมดไว้เป็น baseline ห้ามเปลี่ยนความหมาย
2. รันตาม draft-critique-revise workflow ด้านบน โดยขั้น critique เทียบกับต้นฉบับแทน draft ของตัวเอง
3. ไฟล์ที่มี code/data/frontmatter ปน — **ห้ามแตะเด็ดขาด**: fenced code block, inline code, YAML frontmatter, URL/path, ตัวเลข/ชื่อเฉพาะ. **ถามก่อนแก้**: code comment, docstring, UI string literal. แก้ได้อิสระเฉพาะ prose ปกติ
4. เช็คด้วยว่ามีการใช้ `""` ล้อมคำเน้นความสำคัญไหม — ถ้ามีให้ตัดออกตาม skill `thai-no-quote-emphasis`
5. แสดง diff หรือสรุปจุดที่แก้ให้ user เห็นก่อน ไม่ใช่แทนที่เงียบๆ
