## Thai writing anti-AI-tell rules
เวลา draft เนื้อหาภาษาไทย (งานเขียน, เรียงความ, รายงาน, บทความ, แชท) ให้เลี่ยง pattern เหล่านี้ที่เป็น signature ของข้อความ AI-generated ภาษาไทย:
- **คำเชื่อม essay-formal เปิดย่อหน้า**: ห้ามใช้ "อย่างไรก็ตาม / นอกจากนี้ / ในขณะเดียวกัน / ทั้งนี้ / ดังนั้น" เปิดย่อหน้าเกิน 1 ครั้งต่อทั้งชิ้น และห้าม rotate คำเชื่อมกลุ่มนี้ไม่ซ้ำกันทุกย่อหน้า
- **list สมมาตร 3 ข้อ**: ห้ามยกตัวอย่างทีละ 3 ข้อที่โครงประโยคขนานกันยาวเท่ากันเสมอ — ให้ยก 2 หรือ 4 บ้าง ยาวไม่เท่ากัน และเลี่ยงสูตรเปิด "ไม่ว่าจะเป็น... หรือ..."
- **ประโยคจบแบบ restate ครบ**: ห้ามขึ้นจบด้วย "สรุปได้ว่า / กล่าวโดยสรุป / ท้ายที่สุดแล้ว" แล้ววนทวนทุกประเด็น — ให้จบด้วยความเห็นส่วนตัว/detail คมๆ สั้นกว่าที่อยากจบเสมอ
- **ความยาวประโยคสม่ำเสมอเกินไป + ไม่มี detail เฉพาะตัว**: ต้องมีประโยคสั้นกระแทกแทรกบ้าง สลับกับยาว และงานเล่า/เรียงความต้องมี detail เฉพาะเจาะจงอย่างน้อย 1 จุด (ชื่อ สถานที่ เหตุการณ์ ตัวเลขจริง) ถ้าไม่รู้ให้ถาม user แทนเขียน generic
- **Register**: ต้องรู้ว่ากำลังเขียนแบบไหน (เอกสาร/วิชาการ/บทความ/แชท/สร้างสรรค์) แล้วปรับให้เข้ากับ register นั้น ห้าม default เป็นโทน essay-formal ทุกครั้ง — แชทควรมี particle (อ่ะ/แหละ/เลย/555) ละประธานได้, งานเขียนเล่าส่วนตัวควรมีสรรพนามบุรุษที่หนึ่งและประสบการณ์ตรง
- **nominalization แปลอังกฤษ**: เลี่ยง "มีความสามารถในการ X", "อย่างมีประสิทธิภาพ/อย่างมีนัยสำคัญ" ให้ใช้กริยาไทยตรงๆ แทน (ยกเว้นงานวิชาการแท้ที่ต้องใช้ศัพท์บัญญัติ)
- **หลีกเลี่ยง copula "เป็น/คือ"**: AI ชอบแทนที่ประโยคบอกเล่าตรงๆ ด้วย "ทำหน้าที่เป็น", "ถือเป็น", "สะท้อนให้เห็นถึง", "นับว่าเป็น" — ถ้าพูดตรงๆ ว่า "X คือ Y" ได้ก็พูดตรงๆ ไป ไม่ต้องอ้อม
- **negative-parallelism "ไม่ใช่แค่ X แต่ยังเป็น/แต่ยังรวมถึง Y"**: เป็นแม่แบบประโยคที่ AI ใช้บ่อยเกินจริงเพื่อสร้างมิติปลอมๆ ให้ประเด็นง่ายๆ — ใช้ได้นานๆครั้งจริงๆ ที่มี contrast ชัดเจน ห้ามใช้เป็นโครงประโยคหลักซ้ำๆ ในชิ้นเดียว
- **การอ้างอิงลอยๆ ไม่มีแหล่งจริง**: เลี่ยง "ผู้เชี่ยวชาญระบุว่า", "มีการศึกษาพบว่า", "จากสถิติชี้ให้เห็นว่า" โดยไม่มีชื่อ/แหล่งที่มาจริงรองรับ — ถ้าไม่มีแหล่งจริงให้พูดเป็นความเห็นตรงๆ ("ฉันว่า...") แทนสร้าง authority ปลอม
- **สูตรจบแบบ hedge-แล้ว-เน้น**: เลี่ยงโครง "แม้จะมี [จุดดี] แต่ก็ยังคงเผชิญกับความท้าทาย/ปัญหาอยู่" ปิดท้ายทุกย่อหน้า/ทุกชิ้นงาน — เป็นสูตร AI สร้างความสมดุลปลอมๆ ไม่ใช่การวิเคราะห์จริง
- **สลับคำพ้องความหมายถี่เกินธรรมชาติ (elegant variation)**: AI มักเลี่ยงคำซ้ำด้วยการเรียกสิ่งเดียวกัน 2-3 ชื่อสลับกันในย่อหน้าเดียว (เช่นเรียก "หมา" แล้วเปลี่ยนเป็น "สุนัขตัวนั้น" แล้วเปลี่ยนเป็น "เพื่อนสี่ขา" ในย่อหน้าเดียว) — คนเขียนจริงเรียกซ้ำคำเดิมได้ตามธรรมชาติ ไม่ต้องเลี่ยง
- **โทนโปรโมท/โบรชัวร์ท่องเที่ยวในบริบทกลาง**: เลี่ยงคำบวกเกินจริงพร่ำเพรื่อ เช่น "งดงาม", "เต็มไปด้วยเสน่ห์", "มีชีวิตชีวา", "น่าประทับใจอย่างยิ่ง" ในเนื้อหาที่ไม่ได้ขอรีวิว/โฆษณา — โดยเฉพาะเวลาบรรยายสถานที่/สิ่งของธรรมดาๆ
- **formatting ล้นเกินบริบท**: bold ทั้งย่อหน้า, ใช้ emoji คั่นหัวข้อพร่ำเพรื่อ, เส้นคั่น (---) ก่อนหัวข้อย่อยที่ไม่จำเป็น, สร้างตารางในแชท/เอกสารสั้นทั้งที่พูดเป็นข้อความธรรมดาก็พอ — ใช้ formatting หนักเฉพาะงานที่ user ขอเป็นเอกสาร/สไลด์จริงๆ
- **เนียนสมบูรณ์แบบเกินไป (zero human noise)**: งานคนจริง (โดยเฉพาะแชท/เรียงความเล่าประสบการณ์) มักมีจังหวะพูดติดขัด เปลี่ยนใจกลางประโยค ใช้คำเฉพาะตัวบ้าง — อย่าเกลาทุกประโยคให้เรียบร้อยสมบูรณ์แบบเท่ากันหมด ปล่อยให้มีเสียงพูดจริงบ้างตาม register
- **คำศัพท์ไทยที่ AI ใช้เกินจำเป็น (Thai GPT-isms)**: "เจาะลึก" (delve), "พลิกโฉม"/"เปลี่ยนโฉม" (revolutionize เกินบริบท), "ยกระดับ" (elevate เกินบริบท), "ตอกย้ำ" (underscore), "ตกผลึก" (ใช้นอกบริบทสรุปความคิดจริงๆ), "หลากหลายมิติ"/"รอบด้าน" (multifaceted filler), "โอบรับ" (embrace แปลตรงตัว), "องค์รวม" ใช้พร่ำเพรื่อ — ถ้าจะใช้ต้องใช้เพราะความหมายตรงจริงๆ ไม่ใช่เพราะฟังดูหรู
- **อธิบายเหตุผลแบบตำราเนียนเกิน (over-explained textbook reasoning)**: AI ชอบแทรกคำอธิบายทฤษฎี generic ต่อท้ายทุกขั้นตอนแม้ไม่มีใครถาม เช่น "เพราะการเฉลี่ยยอดขายหลายเดือนช่วยให้ตัวเลขนิ่งขึ้น จึงลดความผันผวนลงได้" ทั้งที่รายงานแค่บอกว่าใช้วิธีอะไรเพราะอะไรก็พอ — จุดสังเกต: ถ้าตัดประโยคนั้นทิ้งแล้วเนื้อหาไม่เสียหาย นั่นคือ filler ตำรา ให้ตัดสั้นลงเหลือแค่ผลที่สังเกตได้จริงจากงานที่ทำเอง
- **overclaim เกินหลักฐาน (evidence overclaim)**: AI ชอบใช้คำสรุปที่ฟังดูมั่นใจ/เด็ดขาดกว่าที่ข้อมูลพิสูจน์ได้จริง เช่น เรียกยอดขายสาขา A ที่สูงว่าเป็น "ตัวตัดสินหลัก" ของรายได้รวม (ทั้งที่บอกได้แค่ว่าสาขานั้นมียอดสูง ไม่ใช่ความสัมพันธ์เชิงเหตุผล), เรียกตัวเลขสองชุดในแบบสำรวจที่สวนทางกันว่า "ขัดกันเอง" ทั้งที่อาจมีคำอธิบายอื่น, หรือสรุปว่าผลต่าง "จึงมาจาก" สาเหตุหนึ่งทั้งที่หลักฐานแค่บ่งชี้ความเป็นไปได้ — แก้โดยลดระดับความมั่นใจของคำให้ตรงกับหลักฐานจริง ("มีแนวโน้ม", "เป็นไปได้ว่า", "มียอดสูงที่สุด" แทน "ตัดสินหลัก"/"พิสูจน์แล้วว่า")
- **แต่งเหตุผล/use case ที่ข้อมูลไม่ได้บอกไว้ (invented justification)**: AI ชอบเติม motivation ให้ตัวเลขที่ไม่มีมูลจากข้อมูลจริง เช่นบอกว่าการเลือกตัวเลือก A "ไม่ให้พลาดสิ่งสำคัญ" ทั้งที่ข้อมูลไม่ได้บอกเรื่องนั้น — ยึดกับสิ่งที่ตัวแปรบอกจริงๆ เท่านั้น ห้ามต่อเติม narrative หรือ interpretation ที่ฟังดูสมเหตุสมผลแต่ไม่มีอะไรรองรับ
- **ปิดทุกช่องเหตุผลจนสมบูรณ์เกิน (closing every logical gap)**: AI มักเขียนสายโซ่เหตุผลแบบ "A จึงทำให้ B เพราะ C ส่งผลให้ D" ที่ปิดทุกช่องไม่เหลือที่ว่าง ทั้งที่ยังไม่มีหลักฐานรองรับครบทุกขั้น — คนเขียนจริงมักอธิบายจากสิ่งที่สังเกตได้ตรงๆ ไม่ปิดทุกช่องเหมือนตอบข้อสอบ แก้โดยเปลี่ยนจากอธิบายเหตุ-ผลครบวงจรเป็นบอกผลที่สังเกตได้จริงพร้อม hedge แทน เช่นจาก "A จึงทำให้ B เพราะ C" เหลือแค่ "ผลที่ได้คือ B ซึ่งน่าจะเกี่ยวข้องกับ C"
- **คำเชื่อมเหตุ-ผลที่ควรเลี่ยงเพราะฟังมั่นใจเกินหลักฐาน**: "แสดงว่า", "จึงทำให้", "เป็นเพราะ", "เหมาะกับงาน...เสมอ" — ใช้ "จากตารางนี้", "พบว่า", "ค่า...สูงกว่า/ต่ำกว่า", "อาจเกิดจาก", "เป็นไปได้ว่า" แทน เพื่อให้ระดับความมั่นใจของประโยคตรงกับหลักฐานที่มีจริง (ยกเว้นมีหลักฐานรองรับตรงๆ ครบจริงถึงใช้คำมั่นใจเต็มที่ได้)
- **โครง "เนื่องจาก...จึง..." สมบูรณ์เกินแม้เนื้อหาถูกต้อง**: แม้ประโยคจะไม่ผิดข้อเท็จจริงเลย โครงประโยคทางการแบบ "เนื่องจาก A ... จึง B" ที่เป๊ะทุกจุดก็ยังอ่านเหมือน AI ได้ (คนละปัญหากับข้อ "ปิดทุกช่องเหตุผล" ด้านบนซึ่งเป็นเรื่อง confidence เกินหลักฐาน — อันนี้แม้เนื้อหาถูก 100% โครงประโยคเองก็ยังดูเป็นทางการ/AI) — แก้โดยสลับเป็นโครงหลวมกว่า เช่นจาก "เนื่องจาก A มาก B จึงอาจสูงได้" เป็น "ในข้อมูลชุดนี้ A มาก ทำให้ B อาจดูสูง แม้ C จะต่ำ" (บอกสภาพที่สังเกตแล้ววางเคียงกัน ไม่ต้อง frame เป็นเหตุ-ผลทางการทุกประโยค)
- **เสนอ future work แบบทางการ/กว้างเกินไป (generic future-work suggestion)**: AI ชอบปิดท้ายด้วยข้อเสนอแนะทำงานต่อแบบเป็นทางการและกว้าง เช่น "อาจปรับปรุงวิธีการเพิ่มเติม" ทั้งที่คนเขียนจริงมักเขียนสิ่งที่ตัวเองจะลองทำต่อแบบเจาะจงกว่านั้น เช่น "อาจทดลองเปลี่ยนค่า X ดูว่าผลดีขึ้นไหม" — ให้เจาะจงและทำได้จริงในงานนี้ ไม่ใช่คำแนะนำกว้างๆ แบบตำรา
- **ใส่ตัวเลขจริงแทนคำคุณศัพท์กว้างๆ ในบทสรุป**: ประโยคสรุปที่ใส่เลขเจาะจง (เช่น "ค่า X ประมาณ 0.xx") อ่านน่าเชื่อและเป็นมนุษย์กว่าประโยคกว้างๆ ("ค่า X อยู่ในระดับสูง") เพราะเลขจริงบอกว่าคนเขียนอ่านผลตัวเองมาจริง — ถ้ามีตัวเลขอยู่ในมืออยู่แล้ว ให้ใส่แทนคำคุณศัพท์เสมอ
- **ตัด modifier/วลีสั้นที่ฟังเหมือนถูกตัดมาจากคำอธิบายยาว**: AI บางทีย่อประโยคจนสั้นเกินจริง เช่น "เพื่อลดจำนวนแถวในตาราง" (รายการอะไร ได้จากไหน ไม่ชัด) — คนเขียนจริงจะระบุที่มาของสิ่งที่พูดถึงให้ครบ แก้โดยเช็คว่าประโยคสั้นๆ ที่ตัด subject/ที่มาออกไปยังเข้าใจได้ครบไหมถ้าอ่านแยกจากบริบท ถ้าไม่ครบให้เติมกลับ
- **register ปนกันภายในเอกสารเดียว ต้องเกลาให้สม่ำเสมอ ไม่ใช่ตัดภาษาพูดออกให้หมด**: ภาษาพูดกึ่งวิชาการ (เช่น "เช็ค", "ถ้าดู...เฉย ๆ") ช่วยให้ไม่ดู AI แต่ถ้าใช้ระดับความเป็นทางการสวนกันในคำใกล้กัน (เอกสารใช้ "ตรวจสอบ" ทุกที่ยกเว้นจุดหนึ่งที่หลุดมาเป็น "เช็ค") จะดูเหมือนแก้ไม่ครบมากกว่าดูเป็น AI — เกลาให้ทั้งเอกสารอยู่ใน register เดียวกันหลังตัดสินใจ register แล้ว (ตามกฎ "Register" ด้านบน) ไม่ใช่ไล่ตัดคำภาษาพูดออกทุกจุดจนกลายเป็นทางการทั้งหมดอีกที
- **คำซ้ำเป็น anchor เชื่อมประโยคที่ AI ชอบใช้แต่ซ้ำเกินในระยะสั้น (repeated discourse-anchor phrase)**: AI ชอบใช้วลีเชื่อมแบบเดิมซ้ำ (เช่น "จากผลที่ได้") เปิดหลายประโยคติดกันในย่อหน้าสั้นๆ เพื่อ signal ว่ากำลังสรุป — คนเขียนจริงจะไม่ทวนวลีเดิมถ้าไม่จำเป็น ตัดออกเมื่อประโยคเข้าใจได้อยู่แล้วโดยไม่มี anchor นั้น (ไม่ใช่แค่คำเชื่อมเปิดย่อหน้าตามข้อแรกของสกิลนี้ — อันนี้คือวลีอะไรก็ได้ที่ซ้ำตัวเองในช่วงสั้นๆ)
- **คำที่แปลตรงตัวแต่ไม่เข้าปาก แม้ความหมายถูก (awkward literal collocation)**: บางคำแปลตรงจากอังกฤษแล้วความหมายถูกเป๊ะแต่คนไทยไม่พูดแบบนั้น เช่น "อ้างอิงผลจาก" (refer to the result) ที่ควรเป็น "พึ่งผล/อิงผล" — เช็คว่าคำกริยา+วัตถุที่จับคู่กันฟังดู idiomatic จริงไหม ไม่ใช่แค่ถูกไวยากรณ์
- **คำซ้ำภายในประโยคเดียว (เช่น ศัพท์เทคนิคซ้ำตัวเองเป็น object ของ preposition ที่มัน derive มา)**: เช่น "ลดจำนวนแถวในตาราง" ที่ขั้นตอน X เพิ่งถูกพูดถึงไปหมาดๆ ในประโยคเดียวกัน — คนเขียนจริงจะตัดคำซ้ำที่ infer ได้จากบริบทอยู่แล้วทิ้ง เช็คทุกประโยคว่ามีคำ/ศัพท์เทคนิคซ้ำตัวเองโดยไม่จำเป็นไหม
- **คำ hedge ระดับภาษาพูดที่ปนอยู่ในประโยคทางการ (เช่น "แค่", "มากแค่")**: "ต่ำมากแค่ 0.xx" มีทั้ง "มาก" และ "แค่" ซ้อนกันฟังเป็นภาษาพูด — ถ้าประโยครอบข้างเป็น register ทางการ ให้ใช้ "ต่ำเพียง 0.xx" ไม่ใช่ signal ของ AI-tell โดยตรง แต่เป็นจุดที่ทำให้ register ไม่สม่ำเสมอ
- **ประโยคสองท่อนที่มีวัตถุร่วม (shared object) แต่เขียนซ้ำชื่อวัตถุทั้งสองท่อน**: เช่น "รองลงมาคือสาขา B ยอดของสาขา A และสาขา B รวมกัน..." — ท่อนสองพูดถึงทั้งคู่รวมกันแต่เขียนชื่อซ้ำอีกที ทำให้อ่านเหมือน AI ต่อประโยคแบบไม่ตัดคำซ้ำ — แก้โดยใช้คำแทน ("สองตัวนี้") ในท่อนที่สอง
- **จุดหยุดพักไม่จำเป็นก่อนคำเชื่อม "คือ" เมื่อประโยคสั้นตรงไปตรงมา**: "เดือนที่ยอดสูงสุดของร้าน คือเดือนธันวาคม" มีวรรคก่อน "คือ" ทั้งที่ไม่มีจังหวะหยุดพักทางความหมายจริง — วรรคที่ไม่มีเหตุผลรองรับเป็นสัญญาณของประโยคที่ประกอบมาไม่เนียน
- **จุดตัดสิ้นสุดการไล่แก้ (diminishing returns signal)**: เมื่อเริ่มมีทางเลือกแบบ "เปลี่ยนหรือเก็บของเดิมไว้ก็ได้" หลายจุดพร้อมกัน นั่นคือสัญญาณว่าเข้าเขต stylistic preference ที่ไม่มีคำตอบถูก/ผิดแล้ว ให้หยุดเกลา เกลามากเกินจุดนี้เสี่ยงย้อนกลับไปดูเป็น AI เพราะ human noise ที่เหลือถูกตัดออกจนหมด
- **อย่าเติม premise ที่ต้นทางไม่ได้ให้มา**: ก่อนเขียนต้องเช็คเงื่อนไขของต้นทางก่อนเสมอ ห้ามสมมติเงื่อนไขเพิ่มเองแล้วเขียนต่อเหมือนต้นทางบอกมา
- **อย่าแต่งคำอธิบายเชิงสาเหตุให้ผลลัพธ์ที่ไม่ได้พิสูจน์**: รายงานตัวเลขหรือผลที่สังเกตได้ตรงๆ ก่อน ถ้าไม่ได้ derive สาเหตุมาจริงอย่าปะติดปะต่อเหตุผลให้ฟังดูสมบูรณ์ และอย่าไล่ enumerate ทุกกรณีย่อยในประโยคเดียวยาว แยกเป็นข้อเท็จจริงสั้นๆ ทีละเส้น
- **ตัวเลขจริงดีกว่าคำคุณศัพท์กว้างๆ**: ถ้าอ่านผลมาแล้วมีตัวเลข ให้อ้างตัวเลขนั้น และเมื่อเจอประโยคที่ "ฟังดู AI" ให้เช็คความถูกต้องทางเนื้อหาควบคู่ไปด้วย ไม่ใช่แก้แค่คำ
- เหตุผล: pattern ชุดแรก (em dash / "" / คำเชื่อมเปิดย่อหน้า) จับได้แค่ระดับเครื่องหมาย/คำ แต่ชุดขยายนี้มาจากการวิเคราะห์ pattern โครงสร้าง/วาทศิลป์ที่ Wikipedia รวบรวมไว้เป็นระบบ (Wikipedia:Signs of AI writing) แล้วแปล/ปรับให้ตรงกับภาษาไทย — ครอบคลุมกว้างกว่าการดักแค่คำ, คนอ่านที่ชินกับข้อความ AI จับ pattern เชิงโครงสร้างเหล่านี้ได้ง่ายพอกันหรือง่ายกว่าคำเดี่ยวๆ ด้วยซ้ำ
- ใช้กับ: ทุก project ทุกครั้งที่ร่างข้อความเป็นภาษาไทย

## Draft-critique-revise workflow
skill นี้มีขั้น critique/revise แยกเป็น **บังคับ** สำหรับงานที่ความนิ่ง/น่าเชื่อถือสำคัญ (รายงาน/บทความ/เอกสารที่จะส่ง/โพสต์ให้คนอื่นเห็น) — **ไม่ใช่ทางเลือก** สำหรับงานกลุ่มนี้ ยกเว้นแชตสั้นๆ/ตอบปกติที่ single-pass พอ:
1. **Draft**: เขียนโดยไม่ยึดโครงตายตัว เนื้อหา/ข้อเท็จจริงมาก่อน — แต่ **register ต้องเลือกไว้ตั้งแต่ขั้นนี้** (ตามกฎ "Register" ด้านบน) ค่อยเกลาแค่สำนวน/คำศัพท์ทีหลัง
2. **Critique**: เทียบร่างกับ checklist ด้านบนทีละข้อ + เทียบกับข้อเท็จจริงต้นทาง (กันความหมายเพี้ยน) จด flag เฉพาะจุดที่ชน
3. **Revise**: แก้เฉพาะจุดที่ flag ไม่ rewrite ทั้งชิ้นใหม่
- แชตสั้น/ตอบปกติในบทสนทนา → single-pass เดิมพอ ไม่ต้องแยกขั้น

## Humanize existing text
เมื่อ user ขอ "humanize ข้อความนี้ / แก้ให้ไม่เหมือน AI เขียน" กับ**ข้อความ/ไฟล์ที่มีอยู่แล้ว**:
1. อ่านต้นฉบับเต็ม เก็บ meaning/claims/รายละเอียดทั้งหมดไว้เป็น baseline ห้ามเปลี่ยนความหมาย
2. รันตาม draft-critique-revise workflow ด้านบน โดยขั้น critique เทียบกับต้นฉบับแทน draft ของตัวเอง
3. ไฟล์ที่มี code/data/frontmatter ปน — **ห้ามแตะเด็ดขาด**: fenced code block, inline code, YAML frontmatter, URL/path, ตัวเลข/ชื่อเฉพาะ. **ถามก่อนแก้**: code comment, docstring, UI string literal. แก้ได้อิสระเฉพาะ prose ปกติ
4. เช็คด้วยว่ามีการใช้ `""` ล้อมคำเน้นความสำคัญไหม — ถ้ามีให้ตัดออกตาม skill `thai-no-quote-emphasis`
5. แสดง diff หรือสรุปจุดที่แก้ให้ user เห็นก่อน ไม่ใช่แทนที่เงียบๆ
