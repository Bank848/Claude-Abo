# ทำไมภาษาไทยใน Word ถึงเพี้ยน — และโมเดล "แยกฟอนต์ตามภาษา"

เอกสารนี้อธิบายเชิงลึกว่าทำไม .docx ที่สร้างด้วย python-docx ถึงแสดงผลภาษาไทยเพี้ยน
ใน Microsoft Word และทำไมการ "แยกฟอนต์ตามภาษา" จึงทำได้ใน run เดียวกัน

---

## 1. Word เลือกฟอนต์ "ทีละตัวอักษร" ไม่ใช่ทีละ run

เข้าใจผิดที่พบบ่อย: คิดว่า 1 run = 1 ฟอนต์ ความจริงคือ run หนึ่ง ๆ พก "ช่องฟอนต์"
ไว้หลายช่อง แล้ว Word เลือกช่องที่จะใช้จาก **ช่วง Unicode ของอักขระแต่ละตัว**:

| ช่องใน `<w:rFonts>` | ใช้กับอักขระ | ตัวอย่าง |
|---|---|---|
| `w:ascii`  | ASCII (U+0000–U+007F) | A–Z, a–z, 0–9 |
| `w:hAnsi`  | High ANSI / ละตินเสริม | ตัวมีเครื่องหมาย, สัญลักษณ์ |
| `w:cs`     | **Complex Script** | **ภาษาไทย (U+0E00–U+0E7F)**, อาหรับ, ฮีบรู |
| `w:eastAsia` | CJK | จีน ญี่ปุ่น เกาหลี |

ผลที่ตามมาที่สำคัญ: ประโยคปนไทย-อังกฤษ เช่น `"รายงาน Sales Report"` ภายใน
**run เดียว** Word จะหยิบ `w:ascii` ให้ "Sales Report" และหยิบ `w:cs` ให้ "รายงาน"
โดยอัตโนมัติ → **เราจึงไม่ต้องตัดข้อความเป็นหลาย run เพื่อแยกฟอนต์** แค่ตั้งสองช่องนี้
ให้ถูก ก็ได้ฟอนต์ละติน 1 ตัว + ฟอนต์ไทย 1 ตัว ในรันเดียว

---

## 2. python-docx ตั้งให้แค่ฝั่งละติน

`run.font.name = "X"` → เขียนแค่ `w:ascii` + `w:hAnsi`
`run.font.size = Pt(16)` → เขียนแค่ `w:sz`
`run.font.bold = True` → เขียนแค่ `w:b`

ฝั่ง complex script (`w:cs`, `w:szCs`, `w:bCs`, `w:iCs`) ถูกปล่อยว่างทั้งหมด ภาษาไทย
จึงตกไปใช้ค่า default/theme ที่มักไม่ใช่ฟอนต์ไทยจริง → เกิดอาการตามตาราง:

| ขาดอะไร | อาการใน Microsoft Word |
|---|---|
| `w:rFonts/@w:cs` | ฟอนต์ไทย fallback → **วรรณยุกต์/สระลอย, ซ้อนผิดตำแหน่ง, ตัวเพี้ยน** |
| `w:szCs` | **ตัวไทยหดเหลือ ~10pt** ทั้งที่ตั้ง 16pt (เพราะ `w:sz` ไม่คุมฝั่ง cs) |
| `w:bCs` | **ตัวหนาไม่ติด**กับตัวไทย (อังกฤษหนา ไทยบาง) |
| `w:iCs` | ตัวเอียงไม่ติดตัวไทย |
| `w:lang/@w:bidi="th-TH"` | **ตัดคำ / เว้นวรรค / จัดชิดขอบเพี้ยน** เพราะ Word ไม่รู้ว่าเป็นไทย |

> ทำไมไม่เห็นใน preview / LibreOffice? เพราะตัวเหล่านั้นเดาภาษาไทยจาก Unicode ให้เอง
> แล้วยัดฟอนต์ที่เดาว่าใช่ให้ แต่ **Microsoft Word ยึดตามค่าใน XML อย่างเคร่งครัด** —
> ซึ่งคือโปรแกรมที่ผู้รับเปิดจริง อย่าตัดสินจาก preview ให้รัน `verify_thai_docx.py`

## 3. แยกฟอนต์ตามภาษา (Latin vs Thai) ทำยังไง

ใน `enforce_thai` และ `style_thai_run`:

- `font` (ค่า default `"TH Sarabun New"`) → เขียนลง `w:cs` = ฟอนต์ฝั่งไทย
- `latin_font` → เขียนลง `w:ascii` + `w:hAnsi` = ฟอนต์ฝั่งอังกฤษ
  - ถ้าไม่ส่ง `latin_font` → ใช้ `font` เป็นฝั่งละตินด้วย (หน้าตาเดียวกันทั้งเอกสาร)
  - ถ้าส่ง เช่น `latin_font="Times New Roman"` → **อังกฤษเป็น Times New Roman,
    ไทยเป็น TH Sarabun New ใน run เดียวกัน**

ตัวอย่าง XML ของ run ปนภาษาหลังตั้งค่า (ลำดับ child ถูกตามสคีมา OOXML):

```xml
<w:rPr>
  <w:rFonts w:ascii="Times New Roman" w:hAnsi="Times New Roman" w:cs="TH Sarabun New"/>
  <w:b/><w:bCs/>
  <w:sz w:val="32"/><w:szCs w:val="32"/>
  <w:lang w:val="en-US" w:bidi="th-TH"/>
</w:rPr>
```

### ลำดับ element สำคัญ
`<w:rPr>` มีลำดับ child บังคับตามสคีมา (`rFonts` → `b`/`bCs` → … → `sz`/`szCs` → … →
`lang`) ถ้า insert ผิดลำดับ Word บางรุ่นจะ **ทิ้ง** element ที่วางผิดที่เงียบ ๆ ทำให้
`cs`/`szCs` ไม่ทำงานทั้งที่เขียนลงไปแล้ว — helper จึง insert ตามลำดับนี้เสมอ ไม่ใช่ append

### ขนาดแยกภาษา (ออปชัน)
TH Sarabun New ที่ขนาดพอยต์เท่ากันมักดู "เล็กกว่า" ฟอนต์ละติน ถ้าอยากให้สมดุล ใช้
`latin_size` แยกได้ เช่น `enforce_thai(doc, default_size=16, latin_size=14)` →
ไทย 16pt (`szCs`), อังกฤษ 14pt (`sz`)

## 4. ระดับที่ต้องไล่ตั้งค่า (enforce_thai ทำให้ครบแล้ว)

แค่ตั้งราย run ไม่พอ เพราะบาง run สืบทอดค่าจาก style/default `enforce_thai` จึงไล่:

1. **ทุก run** ในเนื้อความ ในตาราง (ซ้อนได้) ใน header/footer ทุกชนิด
2. **ทุก style** (รวม Heading) — ใส่ `cs` + mirror `szCs` ที่ระดับ style เพื่อให้
   หัวข้อที่ไม่ระบุขนาดเอง **ไม่หด** และยังได้ฟอนต์ไทยถูก
3. **docDefaults / rPrDefault** — ตาข่ายชั้นสุดท้ายสำหรับ run ที่ไม่ระบุอะไรเลย
4. **theme1.xml** — ใส่ `<a:cs typeface="ไทย"/>` ใต้ majorFont/minorFont เผื่อ style
   อ้างฟอนต์ผ่าน theme
5. **settings.xml** — `<w:themeFontLang w:bidi="th-TH"/>` ตั้งภาษาเชิงซ้อนเริ่มต้นของ
   เอกสารเป็นไทย → ช่วยการตัดคำทั้งเอกสาร

## 5. python-docx vs Claude in Word (Office.js) — คนละเส้นทาง

ปัญหานี้เกิดเฉพาะเส้นทาง **python-docx** เพราะเราเขียน XML ดิบเอง

เวลาใช้ **Claude in Word** (add-in / Office.js) แล้วพิมพ์ไทยออกมามักไม่เพี้ยน เพราะ
ข้อความถูกแทรกผ่าน object model ของ Word เอง — Word จะใส่ฟอนต์ฝั่ง complex script
และ detect ไทยให้อัตโนมัติตาม default ของเอกสาร เราไม่ได้แตะ XML ตรง ๆ

แต่เส้นทาง add-in มีปัญหา **คนละเรื่อง** คือ "จัดชิดขอบแบบไทย (thaiDistribute) ไม่ติดกับย่อหน้าที่พิมพ์ใหม่" ซึ่งอยู่นอกขอบเขต skill นี้ สรุปการแบ่งงาน: ปัญหาฟอนต์ไทย/วรรณยุกต์/ขนาด/หนา/ตัดคำเพี้ยน เกิดกับ python-docx ที่สร้าง .docx ให้ใช้ skill **thai-docx** (นี่)

## 6. เรื่องการติดตั้งฟอนต์

- การ **สร้างไฟล์** ไม่ต้องมีฟอนต์ในเครื่องที่รัน — เราเขียนแค่ "ชื่อฟอนต์" ลง XML
  การแสดงผลเกิดตอนเปิดใน Word บนเครื่องที่ **มีฟอนต์นั้นติดตั้ง**
- TH Sarabun New เป็น 1 ใน 13 ฟอนต์แห่งชาติ มักมีในเครื่องคนไทยอยู่แล้ว
- ส่งให้คนนอกที่อาจไม่มีฟอนต์ → แปลงเป็น **PDF ก่อนส่ง** (ปลอดภัยสุด) หรือใน Word
  ติ๊ก File ▸ Options ▸ Save ▸ "Embed fonts in the file" (python-docx embed เองไม่ได้)

## 7. ก๊อปจาก PDF แล้วอักษรห่างเป็นช่อง ๆ (thaiDistribute)

อาการนี้ต่างจากข้ออื่น เพราะ "ไฟล์/การตั้งค่าถูกแล้ว" แต่ **ข้อความสกปรก**

- ตัวแยกข้อความของ PDF เก็บ glyph เป็นตัว ๆ ไม่รู้จักขอบเขตคำไทย เวลา extract ออกมา
  จึงเดาขอบเขตจากระยะห่างของ glyph แล้ว **แทรกช่องว่างปลอม** ระหว่างพยางค์/ตัวอักษร
  (บางทีถี่ถึงระดับทุกตัวอักษร) และมักมีอักขระล่องหนปนมา เช่น U+200B (zero-width space),
  U+00A0 (no-break space), U+00AD (soft hyphen)
- เมื่อวางในย่อหน้า `thaiDistribute` (กระจายเต็มความกว้างทุกบรรทัด) Word ถือว่า **ทุก
  ช่องว่างคือจุดยืด** → ดึงตัวอักษรห่างออกจากกันเป็นช่อง ๆ
- ตอนพิมพ์เองไม่มีช่องว่างปลอม Word จึงตัดคำด้วยพจนานุกรมไทยเอง การกระจายจึงเนียน

**สรุปสาเหตุ: ไม่ใช่ความผิดของ thaiDistribute** แต่เป็นช่องว่าง/อักขระล่องหนที่ติดมากับ
ข้อความจาก PDF ต้องล้างก่อนวางด้วย `clean_pdf_thai()` (หรือ `add_thai_paragraph(..., from_pdf=True)`,
หรือ `clean_thai_in_doc(doc)` ถ้าเผลอวางไปแล้ว)

วิธีล้างทำ 5 อย่าง: normalize NFC → ลบอักขระล่องหน → แปลง unicode space เป็น space ปกติ
→ ดึงวรรณยุกต์/สระ non-spacing กลับมาติดพยัญชนะ → ลบช่องว่างเดี่ยวที่ขนาบด้วยอักษรไทย
สองข้าง (คงช่องว่างรอบอังกฤษ/ตัวเลข/วงเล็บไว้)

> ข้อควรระวัง: การลบช่องว่างไทย-ไทยจะลบ "ช่องว่างเว้นวรรคที่จงใจ" ในข้อความนั้นด้วย
> สำหรับข้อความจาก PDF มักเป็นช่องว่างปลอมแทบทั้งหมดจึงคุ้ม แต่ถ้าต้องการเก็บการเว้น
> วรรคไว้ ใช้ `join_thai_spaces=False` (แลกกับที่ thaiDistribute อาจยืดบ้าง)

## 8. Word ตัดกลางคำไทย -> อักษรห่างกับ thaiDistribute (สำคัญ)

ต่างจากข้อ 7 (ช่องว่างจาก PDF) — อันนี้เกิดแม้ข้อความสะอาดไม่มีช่องว่าง

- Microsoft Word ในบางสภาพแวดล้อม **ไม่เรียกตัวตัดคำไทย** ให้เอกสารที่สร้างจาก
  python-docx (ตัดบรรทัดเฉพาะที่ช่องว่าง/ZWSP เหมือนภาษาอังกฤษ) ทั้งที่ตัดคำไทยให้
  ข้อความที่พิมพ์เองในตัวโปรแกรม
- พอเจอข้อความไทยยาวไม่มีช่องว่าง + จัดชิดขอบแบบไทย (thaiDistribute) Word ถูกบังคับ
  ให้ตัด "กลางคำ" (เช่น ธนาคารแ / บบ) แล้วกระจายทีละตัวอักษรให้เต็มบรรทัด -> อักษรห่าง
- ยืนยันได้จากการเรนเดอร์ไฟล์เดียวกันใน LibreOffice (ซึ่งใช้ตัวตัดคำ ICU) จะออกมา
  ปกติไม่ห่าง -> แปลว่าไฟล์ถูก แต่ตัวเปิดดูบางตัวไม่ตัดคำไทยให้

วิธีแก้ที่ไม่ขึ้นกับว่าโปรแกรมจะตัดคำไทยเป็นไหม: **แทรกจุดตัดคำเอง** ด้วย zero-width
space (U+200B) ที่ขอบเขตคำไทย โดยใช้ตัวตัดคำ pythainlp (newmm) ZWSP เป็นจุดตัดบรรทัด
มาตรฐานตาม Unicode line breaking (คลาส BA) ที่ทุกโปรแกรมรองรับ -> Word ตัดตรงรอยคำ
ที่เราใส่ ไม่ตัดกลางคำ และ thaiDistribute จะกระจายตรงรอยคำเหมือนข้อความที่พิมพ์เอง

ใช้ `insert_thai_word_breaks(text)` / `break_thai_in_doc(doc)` / `add_thai_paragraph(..., break_thai=True)`
(ต้องติดตั้ง pythainlp) — ใส่ ZWSP เฉพาะระหว่างคำไทย-ไทย ไม่แตะอังกฤษ/ช่องว่าง

> ZWSP ที่ "ขอบเขตคำ" คือของดี (จุดตัดคำ) ต่างจาก ZWSP ที่ติดมากับ PDF ซึ่งกระจาย
> มั่วทุกตัวอักษร (ของเสีย) `clean_pdf_thai` จึงลบ ZWSP จาก PDF ออกก่อน แล้วค่อยใส่
> ZWSP ที่ขอบเขตคำจริงด้วย `insert_thai_word_breaks` — ลำดับสำคัญ: ล้างก่อน ตัดคำทีหลัง
